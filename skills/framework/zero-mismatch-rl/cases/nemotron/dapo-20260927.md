# Nemotron NVFP4 DAPO: five steps completed but the forward was not aligned

This is a **failure case** from 2026-09-27/28, not a solved train-inference consistency recipe. The target was Nemotron-H Lightning NVFP4, the vLLM V2 runner, DAPO Math 17k on GB200; the server used TP1+EP4 and the training actor used PP4. The statistics below come from the rollout and actor old-logprob forward saved in the same round; raw weights, tokens and logs are not copied into this repository. `$WORKDIR/nemotron-dapo-five-20260927/` was the root of the historical artifacts on the cluster at the time and is not guaranteed to be accessible from other machines.

## Why the process failed

The four-layer proxy **did have** a fixed 8K/1K pass artifact for real training forward ↔ inference logprob; the earlier claim that "the four-layer train-inference consistency was never verified" is wrong. It took original model layers `[0,1,5,6]` with layer types `[mamba,moe,attention,moe]`: all operator kinds are present, but it contains an artificial `moe→attention` adjacency that does not exist in the original model, and misses the two real adjacencies `moe→mamba` and `mamba→attention`. The later R19 switched to full PP4, variable-length DAPO and different versions of the quantization/MoE/EP4 implementation; for example the content hashes of `quantized_proxy.py`, `nvfp4_moe.py` and `nvfp4_ep4.py` all differ from the old four-layer artifact. The old pass should be kept as a **scoped success** and cannot be used as current evidence for upgrading the R19 candidate. Five steps exiting normally with finite gradients cannot make up for this coverage gap either. For this task, the user restricted the minimal proxy to fixed input/output token logprob comparisons only, without requiring GSM8K, SFT or RL on it.

Handle similar failures in the following order afterwards, to avoid using expensive full training as a locator:

1. First build a minimal proxy from adjacent layers of the original model covering all necessary adjacencies; this model needs at least `mamba→moe→mamba→attention→moe`, rather than mechanically reusing the old four layers. Freeze the policy, fixed input/output tokens, mask, score semantics and deployed weights, and re-establish a non-empty, original-dtype train-inference comparison with the **current candidate code and backends**; without a current pass artifact, stop full BI training.
2. On the first failing sample, first do a prompt-only first-token comparison, then record the residual/attention/MoE/Mamba/head boundaries layer by layer with the same semantics. After a coarse sweep, inspect only within the candidate interval, and capture **exactly the same operator inputs** to separate upstream propagation from this operator's own difference.
3. Change only one execution factor at a time, e.g. attention backend, packing or Graph, and keep an unchanged negative control; if it improves but does not reach zero, keep localizing and do not declare that factor the root cause.
4. Only after the proxy's original failing case reaches zero, expand step by step to a full zero-update on-policy comparison; then verify backward, effective updates, and the on-policy comparison after every sync. Rerunning five steps cannot replace an earlier failed gate.

## Lessons on backend identity and the BI=0 trial

The θ0 server log of that time, `bi1-diagnostic-r19/serving-run/theta0-recovery-6/server.log`, shows: MergedColumn/RowParallel linear selected `FlashInferFP8ScaledMMLinearKernel`, NVFP4 dense GEMM selected `HummingNvFp4LinearKernel`, the MoE expert instance is `HummingIndexedExperts`, and the all-to-all manager is `FlashInferNVLinkOneSidedManager`. These four belong to different operator/communication boundaries; "FlashInfer is used" does not mean the MoE GEMM or dense W4A16 necessarily goes through FlashInfer.

The isolated BI=0 baseline `baseline-r21/baseline/run/baseline-training-r21/rank3.json` failed during the model forward construction phase with zero optimizer steps; the corresponding `training-host-bi0-r21.log` actually printed `FlashInferCuteDslNvFp4W4A16LinearKernel`, while the experiment code hard-required the validated BI Humming W4A16 kernel, triggering `Expected the validated BI Humming W4A16 kernel`. This is **path selection inconsistent with the experimental assumption**; one cannot simply delete the guard and declare the baseline validated, nor conclude from it which of FlashInfer/Humming performs better. When choosing the baseline again, measure dense linear, MoE expert, all-to-all and attention separately, check each worker's actual selection and same-precision output, and then do an E2E pairing with equal workload.

## The attention-path gap exposed by a real DAPO fail-fast

The new θ0 trial under `proxy5-contiguous-r1/rl-fp8-candidate-r1/bi1/`, with the same candidate FP8 inference package, saved 128 Math17k rollouts with 171,191 valid tokens. The training side used the target `FusedFullAttention`, and before the first optimizer step the comparison found **155,913/171,191** original FP32 old logprobs unequal; `optimizer_steps` is 0 on all four ranks. The originally planned five-step training cannot be written up as completed, and the diagnostic-path passes of r62/r66 cannot be used to cover this failure.

The first real training sample is a 92-token prompt + 123-token response. Its prompt, generated tokens and 123 inference-side original logprobs are fully identical to r61's; yet the new trial's first sample has 121/123 logprobs unequal, max absolute difference `0.34789109230041504`. With **the same θ0, the same saved sample and the same PP4 `train()` + autograd**, switching only the training attention: `ExistingTritonFullAttention` gives 0/123 unequal and `FusedFullAttention` gives 121/123 unequal, the latter matching the real training error on the first sample. Triton here is only a causal control, not a solution that satisfies the final new-kernel constraint.

The per-layer outputs at position 91 of the two training paths are fully identical in layers 0–4, and first diverge at layer 5 (the first full-attention layer): 2,441 BF16 elements of hidden are unequal while residual is still identical. The Q, K, V inputs of layer-5 attention at **all 215 positions** are bitwise identical, yet the direct attention output already has 821,319 unequal BF16 elements, 3,725 of them at position 91; so the difference is inside the attention algorithm/numerical path, not in that layer's QKV projection, earlier layers or the generation trajectory. The artifacts are in `diagnostics/row0000-fused-attention-r4/` and `row0000-triton-attention-r5/` respectively; these are isolated comparisons, and the real path is not yet fixed.

### Follow-up fix on the five-layer proxy: the Q scale must take the real runner value

The isolated candidate wires a fixed-schedule direct-FP8 CuTe FA4 into Nemotron-H's BI=1 path, and the inference-side five-layer proxy's fixed 8192+1024 request passes the BI/PD checks of the actual EP4 runner; the server-side capture and the client-side 1024-token score comparison are in `diagnostics/serving-fa4-proxy-capture-r2/`, the capturer proves freshness for every executed step, and the observation itself did not change tokens or FP32 scores. ### Reusable execution checks from this round

1. When fixing a quantization entry point, check the `nn.Module` registration tree, the quant-method kernel objects and that version's legacy fields at the same time; enumerate the hit count, the specific target layers and each worker's actual selection, and fail closed. Looking only at class names or the declared backend is not enough to prove the target callsite changed.
2. Keep the original failing prompt/checkpoint, but once the generation policy changes, first save the **new** complete token history and then let the actor replay it; do not report new-policy logits against responses generated by the old policy as a fix result for the same rollout.
3. Record provenance separately for the four stages: diagnostic override, no-Graph, formal model code, default Graph; equal Graph/no-Graph outputs support diagnostic equivalence on this input but do not mean Graph can be turned off permanently. For an empty hook/trace, first determine whether the capture mechanism actually executed.
4. First do an independent module VJP on the real triggering input, then a whole-model backward non-zero/finite check; the two answer different questions. If numerical work did not run because of permissions, imports or a missing extension, mark it `inconclusive` / `not run`; do not count it as a pass.

## Transferable judgments

- First tag every result `pass` / `fail` / `inconclusive` / `not run`, bound to the model geometry, policy, code/image, backend and number of valid tokens; "experiment completed" is an execution status, not a numerical criterion.
- The fixed-shape proxy's cross-stack forward did pass once; before upgrading, also check layer-type adjacency, parallelism/backend, source hashes and the target workload. Full real data can expose conditions the proxy did not cover, but the limited pass of an old candidate cannot be extrapolated to a new candidate.
- A fixed replay of the first response token separates "generation trajectory divergence" from the initial forward difference; weights, mask/position, reductions, quantization and complete layer inputs still need to be checked, and a specific kernel cannot be blamed directly from it.
- Internal comparisons may temporarily replace kernels, disable Graph or change packing; the conclusions only apply to that diagnostic path. After restoring the target execution conditions, redo the original failing replay and the quality/performance acceptance.

### Isolated counterexample of lowering `max_num_seqs`

The Mamba scan grid in the trace above was padded to 24 rows many times, so it was hypothesized that lowering
`max_num_seqs` from 64 to 16 could reduce empty decode rows. First, on the same five-layer proxy,
it was confirmed that inference BI/PD for 8192+1024 fixed tokens still passes, then on the same idle
GB200 node A, with the same image and package, the same budget 32,768 and c64
Rust Bench protocol, 64 and 16 were measured separately. After warmup, each group formally ran
256×(8192+1024), ignore EOS; all 256/256 completed, 0 failed,
2,097,152 input and 262,144 output tokens, 0 prefix-cache hits, server exit code 0.

| `max_num_seqs` | output tok/s | mean TTFT | mean TPOT |
| ---: | ---: | ---: | ---: |
| 64 | 15,641.22 | 265.02 ms | 3.83 ms |
| 16 | 10,730.32 | 306.07 ms | 4.49 ms |

16 is about 31.4% slower under this **proxy c64** workload, so this candidate is eliminated and not worth
an additional full θ0 and full E2E. The cause has not been attributed with a trace; a lower concurrency cap may
increase queuing or change batching, and an E2E improvement cannot be inferred from grid padding alone.
These numbers cannot be compared directly with the full 52-layer model's 6515 tok/s, nor do they constitute
training-forward or post-update sync evidence. Raw artifacts are under `shared-fi-r1/` in
`budget32768-maxseq64-c64-proxy-<node>-r1/` and
`budget32768-maxseq16-c64-proxy-<node>-r1/`.

Likewise, on the five-layer proxy, raising BI=1's `max_num_batched_tokens`
further from 32,768 to 65,536 was tried in isolation, with other configuration, node A, image and c64 workload unchanged.
The fixed 8192+1024 inference BI/PD checks passed for both groups; after warmup, each formal
256-request run completed 256/256, 0 failed, 0 prefix hits, server exit code 0.
The proxy output throughput at 32,768 / 65,536 is **15,641.22 / 13,906.90
tok/s**, the latter about **11.1%** slower; mean TTFT 265.02 / 380.97 ms,
TPOT 3.83 / 4.23 ms. So 65,536 is eliminated, with no additional full θ0 or performance
acceptance. These numbers only describe this five-layer proxy's E2E screening result; they cannot be used to infer
52-layer throughput directly, nor to treat increasing the scheduling budget as a general optimization. Artifact:
`shared-fi-r1/budget65536-maxseq64-c64-proxy-<node>-r1/`.
