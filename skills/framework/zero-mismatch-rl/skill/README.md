# Train-inference consistency workflow: C0–C10

Turn train-inference differences into experiments with fixed inputs, fixed weights and repeatability; locate the first divergence, fix or optimize, then return to the real training loop. By default keep the user's model, precision, parallelism strategy and consistency target; the switches, thresholds, pass ranges and implementation paths in historical cases and in implementations already present in training frameworks (such as ready-made true-on-policy logic) are not default configuration for a new model; before reusing one, measure its numerics and training step time. Cases and reference PRs such as Nemotron and DeepSeek only provide implementation experience; they do not specify the model, dataset or hardware of the current task.

Forward consistency, backward conformance to the gradient contract, training quality and performance are each accepted separately; none substitutes for another. User configuration takes priority; recover missing information first from existing source code and the resolved config, and only ask about information that cannot be recovered and affects the choice of approach; which information cannot be recovered and must be asked from a human is listed in [Ask the human first](#ask-the-human-first). Low-precision recipes are chosen by hardware and existing paths, with no default precision, model or framework; changing the model or precision requires re-checking coverage and acceptance evidence.

Before executing, set up a per-task workspace: keep an append-only event log of state changes and decisions, and record provenance (command, code commit, environment pins, timestamp) next to every artifact. Look up mechanisms in [guides](guides/), process rules in [practices](practices/), and details in this directory's [validation.md](validation.md) (admission table, dual-path contract, tiered criteria, three SFT comparisons, two-step RL timeline) and [numerical-contracts.md](numerical-contracts.md).

Organize experiment materials step by step, not as a catch-up at the end: each run has its own run ID, linking config/scripts, execution identity, raw results and conclusions; the step index states the current candidate, failed/excluded items, unverified items and the human-confirmed version. C1 maintains the full tuning comparison table, and C10 references the audited baseline ID; for the archive directory and minimum records see [archive experiment materials by step](guides/debugging-mismatch/06-artifacts.md#archive-experiment-materials-by-step).

## Ask the human first

The items in the table below are not in the source code, resolved config, historical cases or reference recipes; only the person who started the task can decide them. The agent sets no defaults, does not carry them over from other models or tasks, and does not apply the "default, can be overridden" closing style from [operations and handoff](practices/operations-and-handoff.md#job-hygiene). **Before the first GPU request**, ask all items the user did not state in one go; items the user already gave in the task are not asked again and are recorded verbatim.

| Item | What to clarify |
|---|---|
| Goal and scope | BI=1 or BI=0; bitwise 0 diff or an error budget (for a budget, the metric and upper bound); inference only, up to training forward, or including backward / SFT comparison / two-step RL loop |
| Performance budget | Allowed gap of BI=1 relative to BI=0, given separately for each concurrency of the 8K/1K Rust Bench (c=1/8/32/64) and for the rollout stage of the formal recipe (generation time per step); upper bounds for training forward and forward+backward relative to the native path on the main topology, or an explicit statement that none is set |
| Parallelism and hardware | Which parallelisms to enable and which is the main topology; hardware, upper bound on node count |
| Data and evaluation | Training data / reward; the problem set, sampling settings and pass line for quality evaluation, or an explicit statement that it is not done this round |
| Two stop points | Baseline audit after C1, recipe review before C9; the human confirms a specific version (see [Two human stop points](#two-human-stop-points)) |

Record the answers, together with date, verbatim wording and confirmer, in the task's decision record (a `decision` entry in the append-only event log); the C1 audit materials and C9 review materials reference it; it is not changed after seeing results. Every gate of the final acceptance must be traceable back to this record; anything that cannot be traced back only reports measured values and does not declare a pass. A task that never agreed on a performance budget and only looked at the fixed-length bench once discovered after delivery that the actual rollout was twice as slow.

C0's "module inventory and missing backward", "master starting point" and C1's "baseline includes R3/PC" were added from Nemotron: modules missing backward, QAT failing to train, and the R3 overhead of the baseline arm were each discovered one week to one month late because the workflow did not ask.

The train-inference consistency implementation defaults to mLite, because it separates the model, operators and runtime, making it easy to reuse inference forward, integrate backward/STE independently, and keep the existing `verl_mlite` interface and MCore distributed optimizer wrapper; the training baseline follows the default MCore path of the existing verl recipe, without injecting the alignment implementation, and is accounted separately from C1's vLLM BI=0 inference baseline. **mLite does not inherently guarantee 0 diff or better performance**; the target model's parallelism, recompute, checkpoint and online sync capabilities must still be verified with the actual recipe. Both arms go into the same recipe and the same image, with `VLLM_BATCH_INVARIANT` selecting the whole arm, see [bi-switch-recipe](guides/recipe-evaluation/bi-switch-recipe.md); for the delivery contract see [validation.md](validation.md#recipe-and-pr-delivery-contract).

## Do the cheapest failure criteria first

1. Host metadata / shape arithmetic: minimal counterexamples for pure functions and boundary parameterization.
2. Single operator: identical inputs, real dtype/layout, non-finite detection, repeated / cross-process / Graph.
3. Frozen batch replay: the original failing A/C and A/A, comparing all valid tokens.
4. Engine: batch composition, prefill/decode, chunk boundaries, cache/Graph, actual parallelism scope.
5. Real training: non-degenerate reward/advantage, finite non-zero gradients, optimizer step, parameter change, sync, frozen-token alignment after update.
6. Production acceptance: full model, agreed number of steps, update/restore lifecycle, quality evaluation and paired performance.

When a second run adds no localization information, change the probe; not reproduced, empty output, or path not executed are not passes. When the failure is in backward, replaying forward alone is not enough; save the checkpoint, batch, RNG and state and move into a minimal backward experiment. Details in [validation.md](validation.md).

## RL delivery gate

Training and inference use **the same immutable image digest and the same Python/Torch and runtime dependencies** (they may be on separate nodes and processes, but two environments inside the image cannot be used to dodge compatibility); through the actual entry point of the target RL framework, complete at least two real updates, verifying each round original-dtype logprob 0 diff before the update, the actual parameter update, and 0 diff for the new policy after online sync. Saved rollouts, offline replay, a separate image and cold start can only be diagnostics; exporting to disk and cold-starting cannot replace the online-sync acceptance of a resident rollout. This is this workflow's delivery convention, not a technical claim about all RL systems; for the mistake record see [policy-versions](guides/weight-update/02-policy-versions.md#this-mistake-and-the-delivery-boundary).

Delivery form: one vLLM PR, one Megatron PR, one verl PR, one unified image, targeting `vllm-project/vllm:main`, `NVIDIA/Megatron-LM:dev`, `verl-project/verl:main`; non-observability changes in verl are kept to the recipe and image scripts as much as possible. Per [from clean PR to delivery](practices/code-and-delivery.md#step-10-from-clean-prs-to-verifiable-delivery), check the target branches and full diffs, pin cross-repo commits, build the same image from clean source, and fill in the [delivery mapping table](templates/consistency-report.md#delivery-manifest).

## Baseline and consistency run as two parallel lines

- **Baseline line**: C1's BI=0 tuning, backend combinations and multi-round performance evidence; do not sacrifice default performance in advance for consistency; after reasonable tuning, freeze the candidate and wait for human audit.
  - BI=0 candidates are chosen only on BI=0's own performance; whether BI=1 has a matching kernel is not a selection reason; BI=1 is the one that has to close the gap.
  - The precision convention constrains format: the quantization format and group of weights, activations and KV, and the accumulation precision. With the same format, swapping kernels, fused operators or changing accumulation order do not count as changing precision and can be tuning candidates; approximate math functions (fast math) are also allowed, but note them in the audit materials.
- **Consistency line**: does not wait for the baseline; proceeds on the proxy per C2–C8; C9 must still meet admission, and full scale is not started early on the grounds of parallel speedup.
- Share the model/precision/hardware/image contract, isolate code, environment and outputs; consistency patches do not pollute BI=0; when the baseline is not finalized, mark the consistency coverage scope, and re-verify after configuration changes.
- Do not add nodes beyond budget; on a single node, GPU experiments hand off in time slices, and during formal benchmarks do not run the other line's GPU / heavy CPU / I/O work. Final performance-gap acceptance depends on the human-confirmed strong baseline and complete consistency evidence.

## Two human stop points

**After C1: baseline audit.** When measurements are sufficient to support "reasonable tuning", freeze the candidate, report, and wait for confirmation; do not bypass this by continuing to search for the performance limit. Materials: model/weight version, hardware and node count, image digest/build time, code and dependency versions, reproducible launch and Rust Bench commands; weight/activation/KV precision, runner, parallelism and scheduling, Graph/cache state, actual operator backends, stating that BI=0 was not changed by alignment patches; configurations tried and rationale, valid tokens per concurrency, warmup, repeat count, throughput/latency and variance, failed items and uncovered scope; proposed locked configuration, [statistical definition](guides/recipe-evaluation/02-evaluation-and-acceptance.md#pairing-and-computation), repeat count, per-concurrency criteria and budgets, and questions pending human decision. The report must attach the decision record from [Ask the human first](#ask-the-human-first) (including both budgets: bench per concurrency and rollout stage); without it the audit does not pass. Without confirmation, the candidate baseline must not be used as the final denominator; re-audit after changing model/precision/hardware/image; while waiting, hand off or release nodes as needed.

**Before C9: recipe review.** See the gate table. Changes affecting load or numerics/update/sync semantics are re-reviewed; pure path and logging fixes are not re-reviewed.
