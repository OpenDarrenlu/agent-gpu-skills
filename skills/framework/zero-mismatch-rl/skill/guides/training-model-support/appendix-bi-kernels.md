# Appendix: Which kernel each operator uses in BI mode, and at what cost

Read [numerical-contracts.md](../../numerical-contracts.md) first, then build candidates using this page. Look up by operator: each row gives the kernel actually used under BI=1, the cost it pays for invariance, known pitfalls, and directions already tested dead. Numbers come from two lines of work, Nemotron-H (GB200 single node, 4 GPUs) and DS4-Flash (GB200 DP8/EP8); the concrete experiments are in the corresponding cases; only conclusions are given here. When the user asks to optimize only a clearly identified Top-K/index overhead, do not expand it into general whole-model tuning; switching DSLs does not relax the contract either.

## Full output contract of stable Top-K

For equal scores, what determines order (e.g. request-local index)? Determine it from the training side / current baseline first; do not invent a tie-break. Preserve the following behavior:

- Comparison keys for equal scores, conventions for positive/negative zero and NaN/Inf (if inputs allow them); a global batch offset cannot replace the request-local index.
- Output indices and their order, not just the same set; swapping indices with equal scores changes downstream floating-point reduction order.
- Valid length, mask, invalid sentinel, K larger than the valid count, empty rows, padding, tail blocks.
- Prefill/decode index coordinates, cache page mapping, and positions of the same semantic token.

For candidates, check in turn duplicate allocations, sort input ranges, radix/merge passes, workspace, launch/grid/block; prove order is preserved before removing a pass. For CUB/custom sort or selection, verify the binding and the actual lifetime of temporary storage; do not skip integration tests because the library claims to be stable. Pre-generating index/workspace saves overhead, but under multiple streams, concurrent requests and Graph replay it must not overwrite content still in use.

## Index / elementwise fusion

Prioritize confirmed hotspots such as gather lengths, row start/end, sparse index concatenation and invalid-row zeroing. First write out for each row: input coordinates, whether intervals are left-closed right-open, output capacity, valid range, who writes padding.

Fusion can save a launch/temporary tensor, but may also increase register pressure or break memory access patterns; measure gains on all real shapes, do not judge value by lines changed. Shrinking the grid and the loop stride must be changed together to cover the full output; use reused buffers filled with poison values to check whether tails/empty rows are missed.

Indices being integers does not make them inherently correct: off-by-one, request offset, CP boundaries, overflow and uninitialized rows all cause whole-sequence deviation. If fusion crosses into dequant/norm, the original dtype conversions and rounding positions must also be preserved. Unit-test Top-K and index post-processing separately, then combined, module forward, engine gates. Account for whether the optimization also improves BI0: dynamic block/grid selection on a shared path is a general optimization and cannot all be counted as a reduction in BI-specific overhead.

## The M of split-K and grouped GEMM

The M of a GEMM usually means the number of rows processed in this call; masked grouped GEMM computes multiple experts in groups, using only each group's valid token rows. `expert_num_tokens.max().item()` brings the on-device max token count to the Python host and is often used to choose capacity/scheduling hints; it does not automatically "fix the shape" or "guarantee BI". This readback synchronizes and usually cannot be used directly in CUDA Graph capture. Before removing it, read the API: is the parameter a correctness bound, a capacity, or a tuning hint? Restore the library-supported estimate/safe upper bound, covering heavy load and empty experts; do not claim without source evidence that the default kernel necessarily accesses memory illegally when M is underestimated, and do not arbitrarily set a small value to go faster.

One launch per token can avoid some batch-dependent reductions/scheduling, but brings many launches and low utilization. Batched launches after fixing `n_split` may preserve the numerical order of the same row, but the following must also be fixed or verified: the K interval per split, accumulation order within the interval, accumulator dtype, partial reduce order, tail/padding, the actual kernel specialization. "Fixed K/n_split" is a candidate mechanism, not a proof that prefill = decode: if the two paths use different tiles, epilogues, precision or preprocessing, the same split count can still differ. Test identical operator inputs, and also test the full semantic path.

## BI coverage of attention

BI for attention includes QK, online softmax, PV and the merge order across blocks/splits. Beyond fixing the split count, the tile scheduler, Q-stage, cluster/scheduling choice, page layout, mask/sink, score scale, accumulator/rounding may all depend on batch/length. Even if small batches all pass, you must still cover long context, prefill chunk and decode, Graph buckets, mixed batches, page boundaries, and prefix cache hit/miss. Having Graph+prefix enabled does not mean one test actually executed all these branches; record coverage.

## Observation under Graph mode

Save the resolved Graph mode, capture sizes, prefill/decode/mixed step types and evidence of kernel invocation. Successful Graph capture does not guarantee numerics identical to eager, nor that every step takes the same graph. Python hooks usually run at capture and are not re-executed on replay; a capture dump cannot stand for all replays.

When graph replay needs observing, use a controlled device-side output / static diagnostic buffer, and state whether the instrumentation changes the capture. Eager hooks can be used for localization, but final re-verification must return to the original Graph mode. Even if the Graph-off compiled path matches the production Graph on fixed samples, eager may still differ; keep artifacts for all three separately. A hook not firing on the compiled path cannot be interpreted as the layer not executing.

Disabling graphs changes speed, which in turn changes online batching. First fix per-step tokens, requests/neighbors, padding and cache state, then compare the actually supported modes such as eager/FULL/PIECEWISE. Use a 2×2 experiment to rule out dispatch/split plans changed simultaneously by the switch. A short filler may make the mixed step fall into a capture bucket, while a long filler goes eager instead. The full model and a small model differ in prefill/decode overlap; a small model passing cannot cover production mixed steps it did not trigger. For intermittent failures, keep multi-round samples and trigger rates, not only the successful rounds.

## determinism takes effect only on the main thread

In PyTorch 2.13 (nv26.07), Inductor config override values are thread-local (ContextVar). `torch.use_deterministic_algorithms(True)` sets `torch._inductor.config.deterministic` to True on the main thread, while it is still False in autograd's CUDA device thread. A `torch.compile`d norm VJP is first compiled in the autograd thread, during backward, sees `deterministic=False`, and the generated looped-reduction kernel enables `dynamic_scale_rblock`: besides `R0_BLOCK=1024` there is an extra 512 candidate, and the first launch picks by timing. The two have different reduction orders and bitwise-different results. Only at the end of dynamo compilation is that thread set back to deterministic; subsequent compiles have a single fixed config. Result: in the training trajectory, only backward step 0 is not bitwise reproducible across runs; forward logprobs and the RL loop are unaffected.

Apply both fixes: at the compile site, `torch.compile(..., options={"deterministic": True})` (independent of environment); in the recipe environment, add `TORCHINDUCTOR_DETERMINISTIC=1` (covers any "first compile" in the autograd thread, including compilation of vLLM forward functions in recompute). Also: verl's full_determinism actually sets `warn_only=True`, and mamba_ssm SSD backward must have deterministic mode enabled explicitly.

## How to break down the cost from BI0 to BI1

First draw the actual call chain, making explicit what the default fast kernel, the BI branch, and the extra preprocessing/sorting/postprocessing each are. Do not infer "split-K was changed" or "a temporary Triton was used" from function names. Compare source, binding, build artifacts, and real launches.

You may copy the BI0 implementation into a separate candidate, then add deterministic/BI conditions one by one, for bisectable A/B; it need not be in the same file, but the default path must be kept unchanged. If the BI0 algorithm cannot implement the required tie/reduction contract, switching algorithms is also allowed, with the cost stated explicitly.

Fairness between the two arms comes before any kernel conclusion: same fabric (on DS4 two environment variables closed most of the remaining gap; numbers in the [DS4 case](../../../cases/deepseek-v4-flash/README.md#serving-performance-levers-gb200-dp8ep8)), same node, same image, BI=0 not needlessly running BI kernels, no JIT stalls, KV zeroing fix present in both arms. Nemotron BI1 vs BI0 E2E throughput loss is taken as the median of 5 pairs, with single pairs reported separately; numbers in [delivery results](../../../cases/nemotron/results/final/README.md#conclusions).

## Minimal record per candidate

```text
baseline / candidate source+binary hashes
one intended change; BI-specific or common
same-input bitwise + BI composition + prefill/decode gates
BI0 unchanged + real shape/tie/mask/tail + Graph/workspace reuse
paired latency, launch/allocation counts, repetitions
pass / fail / inconclusive; retained or rejected; remaining scope
```

On failure, first save the minimal counterexample, then pull it out of the default path. When the user requires all micro tests to pass before E2E, do not skip the gates; correctness failures must not be overridden by performance numbers. An existing stable-sort patch must not be quietly removed in order to reproduce a long-length mismatch; that tests a regression, not a defect of the current best code.
