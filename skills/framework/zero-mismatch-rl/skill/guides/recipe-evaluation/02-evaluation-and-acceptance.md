# Evaluation contract and paired acceptance

Each artifact answers only one question. Bitwise logprobs on fixed tokens only prove the scoring of the same token history; natural-generation tasks (GSM8K, AIME) answer quality; fixed-length load (Rust Bench) answers throughput. The token sets and timing differ, so they cannot substitute for each other. After a change to the numeric path, deployed weights, or backend, every in-scope quality and speed check needs independent evidence for the **current candidate**; out-of-scope items are marked unverified, and no new acceptance tasks are added on your own. Concrete numbers are in cases ([Nemotron-H](../../../cases/nemotron/README.md), [DAPO case](../../../cases/nemotron/dapo-20260927.md)).

## Evaluation contract

If any of these six items differs, it is not the same score: dataset version (AIME24 ≠ AIME25), prompt/chat template and thinking mode, sampling parameters (temperature/top-p/top-k, stop tokens; greedy n=1, sampled average, and pass@8 differ; pass@1 with n=8 is not greedy accuracy), number of repeats, grader (answer-region detection, boxed extraction, tail truncation length, reward extractor), length cap (the training cap and the eval cap may differ; a 4K vs 8K result difference is not purely model capability).

- A 30-problem set has coarse resolution and real sampling noise. Under greedy, n repeats give the same result, so the score is a multiple of 1/30 (3.33 points). Sampled, the noise is still large: Model A evaluated the same step-45 weights twice (8 samples per problem) and got accuracy 0.650 vs 0.679 and pass@8 0.80 vs 0.90. Measure this repeat noise once per task and read curve differences against it.
- Read the framework's score scale before quoting it. SkyRL's `eval/*/avg_score` is the mean of a +1/−1 reward, so accuracy = (avg_score + 1) / 2 (Model A step 0: 0.275 → 0.638), and it logs no maj@k; compute maj@k and accuracy offline from the per-sample eval dumps (turn them on, e.g. `trainer.dump_eval_results`) with the run's own grader, and check the recomputed scores equal the logged ones.
- Rising training reward, probs_diff of 0, and held-out improvement are three conclusions that do not substitute for each other; dynamic sampling changes the sample composition of training reward. Read truncation rate together with the accuracy of completed answers, and state separately whether the gain comes from completing more answers or from completed answers being more accurate; 4096 is the task setting, do not relax the budget and re-evaluate to "eliminate" truncation ([03 §2](03-day0-baseline-hparams.md#2-default)).
- Gains from relaxing the token budget are not training improvement. Charts come from raw metrics; do not fabricate a step 0.
- W&B checks: the run config behind a curve, the step basis (rollout step or optimizer step), and the checkpoint version must be traceable; when metrics are cumulative, take per-phase differences.

### Three grader checks

When the reward misjudges, training still runs, the curve still rises, and the train-inference consistency check cannot catch it either (both sides are fed the same token string).

1. **Before training, a known-answer test.** Take a few base answers manually confirmed correct and run them through the grading function as-is (including all special tokens at the end of the answer); the pre-training eval reports the number of completed answers, how many of those are judged correct, and the number truncated at the same time. If the fraction judged correct among completed answers is far below expectation, it is a grading problem. In a later version of Model C (2026-10-13), a hand-written driver passed vLLM completion `text` directly to verl `math_dapo.compute_score`, with the end token at the end of the text: the grader takes the whole line after `Answer:`, so plain numeric answers were judged wrong, while `$...$` answers were judged correct because only the content inside the dollar signs was taken. Pre-training AIME showed 3.75% (actually 49.2%), and 32.9% after 10 steps (actually 48.3%); the entire gain was the model learning to add dollar signs. Of 123 completed answers only 9 were judged correct, and that single number exposes it. Strip the end token only at the end of the text (regex anchored at `$`), not by cutting at the first occurrence: the end of the thinking segment has the same token.
2. **During training, format-agnostic accuracy.** verl `math_dapo` (main `5b550b0c`) only looks at the last 300 characters of the answer: by default it first accepts an `Answer:` line, and only looks for `\boxed{}` if none is found; with `strict_box_verify` on, it only accepts `\boxed{}` in the last 100 characters. In one model's LoRA training, step 1 had 37/256 final boxed answers correct but judged -1, dropping to 0 by step 16: the reward increase over the first 20 steps was mainly format learning. Before reporting "reward is rising", compute a format-agnostic accuracy column from the rollout dump (the last boxed after the thinking segment equals the reference answer) and put it next to the graded accuracy; until the gap between them converges, rising reward does not count as capability.
3. **When switching graders or migrating the reward handler, compare offline.** Run both scorers offline on the same batch of responses and inspect only samples where the verdicts differ; do not swap the scorer just to "align", which would misjudge another model's valid output because of format differences. Concrete handler differences are in §8.2 of the Miles recipe audit (not included here).

If accuracy multiplies in a short time while answer length stays the same, first compare the last line of two answers to the same problem, before and after.

## Paired acceptance

**Freeze the criteria first, then run.** Fix model/checkpoint content, image digest, source/overlay, hardware/nodes, runner/parallelism, weight and KV precision, the actual backends for attention/dense GEMM/MoE/all-to-all, and the resolved config for Graph and cache; write down what is compared, how it is computed, the pass line, and the noise floor; plant a known error to confirm the criteria can return FAIL. BI=0 is first tuned to a reasonable strong baseline at the agreed precision and audited by a human; do not downgrade it to shrink the gap. If the candidate changes quantization dispatch, attention, MoE, exported weights, or the image, re-evaluate which old evidence is invalidated ([evidence ledger](../../practices/evidence-and-experiments.md#6-candidate-evidence-ledger)).

**List confounders first, then compare.** First list every difference between the two arms in a table; each item is either aligned or quantified separately; a difference where several things changed together is not attributed to a single switch. Example: the two Nemotron-H arms differed simultaneously in PC on/off, `gpu_memory_utilization`, training backend (Bridge vs mLite), and R3 return path; concrete values in [cases/nemotron/recipe.md](../../../cases/nemotron/recipe.md).

**Quality pairing**: same problem IDs, template, seed, sampling parameters, max length, scorer, no retries; record per problem whether each side is correct, and `both_correct`/`only_bi0`/`only_bi1`/`both_wrong` must sum to the total number of problems; report each side's score, the absolute percentage-point difference, and the agreed threshold. Similar scores do not mean per-problem identity, and passing quality does not mean bitwise-equal logprobs.

**Fixed-length throughput**: the agreed load is vLLM Rust Bench 8192 input/1024 output, ignore EOS, c=1/8/32/64; record actual input/output tokens, completed requests, error count, warmup, wall time per concurrency point, throughput, and TTFT/TPOT. If there is also a real rollout load, list it separately; do not mix fixed-length and natural-EOS results into the same ratio.

**Rollout phase**: short runs of both arms of the same formal recipe (same image, same node count, same data, same seed, differing only in the BI switch); the metric is [RL per-step gen time](../performance-profiling.md#three-throughput-metrics) (makespan), and the number of generated tokens is also recorded; pair by step, and first measure same-arm repeat noise. It is the second performance acceptance item for train-inference consistency; its budget is likewise frozen by a human before testing and is not derived from fixed-length throughput.

## Pairing and computation

Frozen by a human before testing: number of repeats, pairing order, aggregation formula, the budget/pass rule for each target c and for the rollout phase, how invalid legs are judged and re-measured; the budget can only come from a human — if there is none, ask; no default. Recommended: the median of per-round paired loss `median_r(1 - T_BI1[c,r] / T_BI0[c,r])`; if you choose `1 - median_r(T_BI1[c,r]) / median_r(T_BI0[c,r])`, record it explicitly as "ratio of median throughputs". The two statistics are not equivalent and you cannot switch after seeing the results; while the statistic has not been reviewed, only report measurements and do not declare the budget passed. Historical results keep their original formula and are not silently re-judged under a new one.

1. Each leg records on every worker the image/package hash, actual kernels/backends, resolved config, Graph state, cache hits, and request and token stats; normal exit of client and server is verified separately.
2. Same node, same resources, no interfering load, alternating order (AB/BA/AB), each side warmed up separately each round; do not pair the fastest run of each from different node pools.
3. First check workload and exit receipts item by item. A mismatched leg is judged `inconclusive`; BI loss cannot be computed from throughputs with different request volumes.
4. Report each round's raw throughput and loss `1 - T_BI1/T_BI0`, then compute the formal result per c with the reviewed formula; keep failed/invalid rounds and the reason for re-measurement. Averaging across c must not hide a required c exceeding the limit; a single-round exceedance and an aggregate exceedance are reported separately.

Optimization screening may first test only the previously failing concurrency points, but that only decides whether it is worth continuing. Take the median over multiple pairs and report single pairs separately: when a candidate's single round sits right at the budget line, it cannot pass against an old baseline's historical median; both sides must be re-paired alternately on the same node, same image, same time window. When the candidate changes the model output path, the old candidate's quality and post-update alignment evidence cannot be carried over either. Alternating pairing does not automatically guarantee that the denominator is a strong baseline: when clear fast/slow modes appear under the same config and workload, keep per-round raw numbers and check tuning receipts, CPU/GPU state, Graph, cache, and actual operator selection; do not declare an optimization effective because BI=0 happened to land in a slow mode and the loss shrank. For unexplained fluctuations, mark causal attribution `inconclusive`; any formal target point that exceeds the budget under the predetermined rules is still `fail`, and you may not pick rounds or switch aggregation formulas after the fact.

Profiling runs only outside the formal profiler-free E2E measurement; GPU kernel durations may overlap and cannot be summed in place of E2E; a kernel name is not a module identity, see [Performance and profiling](../performance-profiling.md).

## Failure and recovery

When the acceptance checker errors, first distinguish producer, numerics, scorer, and parser. If the raw worker/server receipts and scores are sealed, and the wrapper misparsed them due to a schema change, keep the original artifacts and read them with a **separately versioned, hash-recorded** recovery checker; the recovery checker must verify all workers, EngineCore, API server, package identity, and workload, and keep the original failure status. It can only correct control-plane conclusions; it cannot fabricate missing numbers, unfinished requests, or failed service exits.

Keep failure records as-is and append new results; distinguish reruns from swapping problems. The final report lists at least, separately: train-inference forward, module backward, real update/sync, quality, performance, clean exit, final immutable artifacts; each cell is `pass`/`fail`/`inconclusive`/`not run`. The [Nemotron DAPO case](../../../cases/nemotron/dapo-20260927.md) is a concrete scope of "five steps bitwise pass, GSM8K pairing pass, but first-round c=32/64 performance over budget".
