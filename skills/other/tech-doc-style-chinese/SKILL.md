# 中文技术文档与技术原理报告规范（GPU / AI Infra 定制版）

<!-- 上游：Fenng/Tech-Doc-Style-Chinese（MIT，作者 Fenng，GitHub：@Fenng），基线 commit b119d01。本地定制说明见 README.md。 -->

## 适用范围

本 Skill 是上游通用规范的同名本地覆盖版：保留上游全部通用规则，并为 GPU 算子、推理框架和训练框架方向的技术原理报告增加结构模板、术语表、证据与数字规范。

技术原理报告类：

- 算子与 kernel 设计/原理报告、实现说明和 PR 设计说明
- 性能分析与优化报告（ncu、nsys、IKET、benchmark、roofline、性能建模）
- 推理框架机制解析（SGLang、vLLM、KV cache、调度、attention backend、并行与通信）
- 训练框架与 RL 后训练原理（verl、FSDP、Megatron、并行策略、显存与通信账本）
- 训推一致、确定性和数值一致性分析
- 技术选型与方案对比、论文/上游 PR/源码解读
- 把截图、笔记、聊天记录、profile 输出整理成文章

通用文档类（上游原有）：文档首页、产品介绍、更新日志、API 文档、错误码、常见问题、操作手册、故障排查、运维 Runbook、安全说明和界面文案。

不要改写机器可读内容：代码字面量、JSON 键名、URL、API 路径、命令、配置项、环境变量、kernel 名和模板实例化、PTX/SASS 指令、ncu metric 名、commit hash、shape 元组和 dtype 字面量。

## 规则优先级

发生冲突时，按以下顺序处理：

1. 保留事实、逻辑、限制、安全信息和法律含义；技术报告还包括证据等级、测量条件和确定程度。
2. 服从用户明确要求和目标项目约定。
3. 保持技术术语和机器可读内容准确。
4. 改善结构、语义、语气和可扫读性。
5. 最后处理标点、留白、大小写等排版细节。

不得为了句子更短、语气更确定或格式更统一而牺牲更高优先级的信息。

## 事实保真

- 不新增原文或可靠上下文没有提供的日期、数字、时限、SLA、能力、条件、因果关系或结论。
- 不编造性能数字、硬件参数（SM 数、带宽、峰值算力）、metric 值、源码路径、函数名、commit、配置默认值或论文结论。硬件和软件参数从用户数据、本地参考 skill 或官方资料获取，并注明来源。
- 不删除前置条件、适用范围、例外、风险、兼容性说明或失败处理。
- 不把可能、计划、预计、理论上、通常等不确定表达改成确定事实；不把估算写成实测。
- 信息不足时保留原意，或在正文中标记「〔待确认〕」「〔待补充〕」，括号内可以注明缺什么；不要自行补全。模板中的 `<…>` 是填写提示，交付前全部替换。
- 改写引用、法规、合同、错误原文或用户提供的固定文案时，优先保持原文并将建议单独列出。

示例：

- `截止 4 月 12 日` -> `截至 4 月 12 日`
- `比 baseline 快很多` -> `相对 baseline〔版本待确认〕加速〔待补充〕×〔shape 与 GPU 待确认〕`
- 不要凭空补成 `在 B200 上加速 1.8×`

## 证据等级

技术报告中的关键结论、数字和图都要标注证据等级。结论的确定程度不得高于支撑它的最高证据等级。

| 等级 | 含义 | 必须同时给出 |
| --- | --- | --- |
| 示意 | 帮助理解的概念图或简化模型 | 简化了什么 |
| 设计 | 提案或实现的设计意图，尚未用其他证据验证 | 对应的设计文档或代码位置 |
| 引用 | 论文、官方文档、他人文章或 PR 中的说法，未经本人验证 | 出处 |
| 源码 | 阅读源码得出的行为 | 文件路径、函数名、commit 或版本 |
| 估算 | roofline、解析模型或手算 | 公式、参数取值和峰值口径 |
| 编译产物 | PTX、SASS、IR、`ptxas -v` 资源报告 | 编译命令、编译器版本、目标架构 |
| 实测 | ncu、nsys、IKET、benchmark、日志指标 | 硬件、软件版本、shape/dtype、命令和统计方式 |

详细写法、数字规范和回归样例见 [证据与数字规范](references/evidence-and-numbers.md)。

## 先判断任务模式

### 撰写

- 先确定报告类型、读者、事实来源、发布载体和篇幅。读者通常分为同方向工程师、相邻方向工程师（如框架工程师读 kernel 报告）、技术负责人和外部社区。
- 缺少会改变结论的事实时，先标记缺口，再继续组织可确认内容。

### 改写

- 保留事实、逻辑关系、信息层级、限制和必要例外。
- 默认交付完整改写稿；重大语义选择或待确认内容另行说明。

### 校对

- 只处理约定范围内的错字、标点、留白、大小写和术语一致性。
- 未经要求，不改变结构、语气或事实表达。

### 审阅

- 先列问题，再给建议；按影响程度排序并引用具体原文。技术报告优先审阅证据缺口、口径错误和过度结论，其次才是文字。
- 未经授权，不直接修改文件。

### 整理

- 适用于把截图、笔记、聊天记录、profile 输出或 PR 讨论整理成文章。
- 保留原文表述、数据和图中信息；图按原意重绘，不改数据。
- 原材料之外新增的解释、背景或推导标记为补充：Markdown 中行内写「〔补充〕」，成段内容写成以「〔补充〕」开头的引用块；HTML 中使用模板的补充徽标。读者能区分原文与补充。
- 原材料缺失或看不清的内容标「〔待确认〕」，不猜测。

## 核心写作规则

### 语义与语气

- 准确先于修辞，清晰先于热闹。
- 使用克制、直接、可执行的中文。
- 避免问候式开场、宣传口号、空泛形容和连续堆叠黑话；避免「零开销」「完美重叠」「遥遥领先」等无法验证的绝对化表述。
- 默认使用无主句或「本文」「本实现」；描述作者实际做过的实验和决策时可以使用「我们」；不使用 `你`、`您`。

### 结构与句子

- 一个段落承载一个主要信息点；一个句子保持一个清晰的主干。
- 列表项保持相同层级、句式和信息密度。
- 标题反映用途。技术报告的标题优先写成问题或结论，例如「decode 阶段为什么需要 split-KV」，而不是只写「split-KV」。
- 指代可能不清时，用具体名称替代「该」「其」「此」「上述」。

### 技术报告专用

- 结论先行：开头用 3 至 5 句交代问题、方法、关键数字及其条件、结论和主要局限。
- 一节回答一个问题；章节顺序跟随读者的理解顺序，而不是作者的探索顺序。探索过程放附录或链接。
- kernel 类内容按「算子语义 → 并行划分 → 数据搬运 → 计算 → 同步 → 输出」展开；框架类内容按「请求或训练 step 的生命周期 → 关键数据结构 → 关键路径源码 → 配置与默认值 → 性能影响」展开。
- 先给直觉，再给公式，再给代码。每个公式先定义符号和单位。
- 每个数字带单位和条件；每个加速比带基线；每个百分比说明分母。
- 区分容易混淆的概念：算子与 kernel、occupancy 与 SM 利用率、带宽与吞吐、确定性与 bitwise 一致、标称峰值与可达峰值。完整列表见 [GPU 术语表](references/gpu-terminology.md)。
- 写清提案与已实现的区别：提案用「计划」「预计」，已观测的行为用「实测」「已验证」。更新报告时删除过时的预测。

### 术语与排版

- 同一概念使用同一首选术语，不因追求变化而替换同义词。GPU 领域术语按 [GPU 术语表](references/gpu-terminology.md) 处理：kernel、warp、tile、epilogue 等保留英文；寄存器、共享内存、流水线、访存等使用中文；缩写首次出现给出全称或中英对照。
- 中文正文使用直角引号 `「」`，嵌套引用使用 `『』`；项目、地区或固定引用规范可以覆盖。
- 在可见正文中，中文与英文、阿拉伯数字和版本号之间加一个半角空格；数字与单位之间加一个半角空格，例如 `耗时 200 µs`、`80 GB HBM`。
- 中文与行内代码之间加一个半角空格；链接按显示文字判断留白。中文全角标点前后不额外加空格，不修改代码、链接目标、官方名称和用户指定字面量。
- 张量 shape 写作 `[B, S, H, D]`，tile 尺寸写作 `128×128×64`（M×N×K），dtype 使用大写 `BF16`、`FP8（E4M3）`。
- 中文段落在源文件中保持一段一行，不为了控制行宽做硬换行；代码块、表格、标题和列表结构保持原样。
- 不直接批量运行排版替换工具；先保护 Markdown、代码和机器可读内容。

详细规则见 [术语与排版](references/terminology-and-typography.md) 和 [图表、公式与代码](references/figures-formulas-code.md)。

## 按内容类型处理

### 技术原理报告

先判断报告类型，再读取 [报告结构模板](references/gpu-report-structures.md) 中对应的骨架和必答问题：

| 类型 | 读者要带走的核心问题 | 证据通常来自 |
| --- | --- | --- |
| 算子/kernel 原理与设计 | 算什么、怎么并行和搬运、为什么快、数值是否正确 | 源码、编译产物、实测 |
| 性能分析与优化 | 瓶颈是什么、证据是什么、下一步按什么顺序做 | 实测、估算 |
| 推理框架机制解析 | 一个请求经过哪些模块、关键数据结构和配置如何影响性能 | 源码、实测 |
| 训练框架与 RL 后训练原理 | 一个训练 step 的数据流、资源放置、并行策略和显存/通信账本 | 源码、估算、实测 |
| 训推一致与数值一致性 | 差异有多大、来自哪里、能否消除、代价是什么 | 实测、源码 |
| 技术选型与方案对比 | 在什么前提下选哪个方案、什么条件下应改选 | 估算、实测、引用 |
| 论文/上游 PR/源码解读 | 原文主张什么、机制是什么、哪些已被我们验证 | 引用、源码、实测 |

### API 文档

- 请求方法、路径、字段和值使用代码环境保护；参数写清类型、单位、默认值、限制和是否必填。
- 状态和错误文案根据实际语义翻译；写明前置条件、成功结果、失败结果和恢复方式。详见 [API 状态与错误文案](references/api-status-copy.md)。

### 界面文案

- 按钮说明动作和目标；错误提示说明发生了什么、影响是什么，以及如何恢复；危险操作写清对象、后果和是否可撤销。

### 操作、复现与故障排查

对操作手册、复现步骤、benchmark 流程、故障排查、运维 Runbook 和多步骤 API 流程，读取并应用 [受控中文技术写作](references/controlled-technical-chinese.md)。报告中的「复现」章节也按这一规则写：前置条件在前，一步一个动作，写明预期结果。

## 产出格式

用户未指定格式时按场景选择，规则详见 [产出格式](references/output-formats.md)：

- Markdown：内部设计文档、PR 说明、进 git 的报告（如 `profile/<run>/REPORT.md`）、知乎或飞书草稿、篇幅短或以文字为主的报告。
- 单文件 HTML：从截图或资料整理的文章、对外分享的长文、需要 3 幅以上精确示意图（数据流、流水线时序、内存布局）的报告、需要交互（切换 shape、折叠证据）的报告。起点模板为 [assets/report-template.html](assets/report-template.html)。
- 无法判断时使用 Markdown，并说明可以转为 HTML。

## 与其他 skill 的分工

本 Skill 只负责表达和结构，不替代技术验证。报告中的技术事实和证据先从对应 skill 获取：kernel 实现找 `gpu-kernel-authoring-router`，性能证据找 `ncu-report-skill` 或 `gpu-performance-router`，建模估算找 `nv-gpu-kernel-performance-modeling`，推理框架找 `sglang-skill` 或 `llm-serving-router`，RL 后训练找 `verl-skill`，bitwise 训推一致找 `train-inference-consistency`，通信找 `gpu-communication-libraries` 或 `nccl-skill`，TileLang 设计文档同时参考 `writing-tilelang-design-docs`。性能报告覆盖 `ncu-report-skill` 报告模板的全部章节，可以作为其 `REPORT.md` 的中文写法。

## 项目覆盖规则

先检查目标项目自己的 `AGENTS.md`、术语表、品牌规范、既有文档和用户指示。不要把本 Skill 仓库中的示例约定当成目标项目约定。需要建立项目覆盖文件时，参考 [项目覆盖模板](references/project-overrides-example.md)，并将实际文件放在目标项目中。

## 编辑流程

以下流程按任务模式选择执行；校对只执行约定范围内的检查和修改。

1. 确认任务模式、内容类型、报告类型、受众和项目约定。
2. 标记事实、数字、限制、引用和机器可读内容，建立不可改动边界；为每个关键结论标注证据等级。
3. 修复语义错误、歧义、遗漏、口径错误和不一致。
4. 调整信息顺序、段落、标题和列表；技术报告检查是否结论先行。
5. 处理语气、术语、标点、留白和大小写。
6. 对照原文复核事实、条件、否定范围、因果关系、确定程度和证据等级。
7. 运行适用的轻量检查器，并人工判断警告和风格提示。

## 最终检查

- 是否新增了来源不明的日期、数字、时限、能力、硬件参数或结论
- 是否遗漏了条件、例外、风险、单位、默认值或恢复方式
- 每个性能数字是否带有硬件、软件版本、shape/dtype 和测量方式；每个加速比是否带基线
- 估算、编译产物和实测是否分开；结论是否强于证据
- 主语、对象、否定范围、因果关系和确定程度是否保持准确
- 同一概念是否使用同一术语；缩写首次出现是否有全称
- 每幅图是否有编号、标题、证据等级和一句话结论
- 代码、路径、字段、命令、metric 名和引用是否保持原样
- 段落是否残留硬换行，拼接边界的中西文留白是否正确
- 项目覆盖规则是否来自目标项目，而不是示例文件

## 自动检查

```bash
# GPU 技术报告：在上游规则之外启用 GPU 术语大小写、中西文与单位留白、加速比与尺寸写法、绝对化与模糊量化表述、领域错词和术语一致性检查
python3 scripts/lint_copy_rules.py --profile gpu report.md

# 检查并展开段落硬换行
python3 scripts/unwrap_md_paragraphs.py --check report.md
```

检查结果分为 `error`、`warning` 和 `style`。自动检查不能证明语义正确，事实保真、证据等级和口径仍需人工复核。
