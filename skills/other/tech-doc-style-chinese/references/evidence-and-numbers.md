# 证据与数字规范

仅在技术报告涉及性能数字、测量结果、估算、源码结论或因果判断时读取本文件。本文件是上游「事实保真」规则在 GPU 技术报告中的展开：不补造数字，不提升确定程度，不混淆证据类型。

## 证据等级

| 等级 | 含义 | 必须同时给出 | 标注示例 |
| --- | --- | --- | --- |
| 示意 | 帮助理解的概念图或简化模型 | 简化了什么 | `图 2｜流水线示意（示意，忽略 epilogue）` |
| 设计 | 提案或实现的设计意图，尚未用其他证据验证的行为 | 对应的设计文档或代码位置 | `按设计，TMA 加载与 MMA 可以重叠（设计，待 IKET 验证）` |
| 引用 | 论文、官方文档、他人文章或 PR 中的说法，未经本人验证 | 出处 | `据 FlashAttention-3 论文……（引用）` |
| 源码 | 阅读源码得出的行为 | 文件路径、函数名、commit 或版本 | `源码：radix_cache.py::RadixCache.match_prefix @<commit>` |
| 估算 | roofline、解析模型或手算 | 公式、参数取值和峰值口径 | `估算上限 3.2 TB/s（峰值取自〔来源〕）` |
| 编译产物 | PTX、SASS、IR、`ptxas -v` 资源报告 | 编译命令、编译器版本、目标架构 | `ptxas 报告每线程 168 个寄存器（编译产物）` |
| 实测 | ncu、nsys、IKET、benchmark、日志指标 | 硬件、软件版本、shape/dtype、命令和统计方式 | `实测中位数 41.2 µs（20 次）` |

使用规则：

- 每个关键结论、数字和图都能对应到一个证据等级。
- 结论的确定程度不得高于支撑它的最高证据等级。只有估算时，不写「达到」「实现了」。
- 不同证据等级不放进同一列数字：估算列和实测列分开。
- 同一幅图出现多个证据等级时（例如 roofline 图中的估算上限与实测点），用不同图形元素区分并在图例中标注。编译器事件顺序和运行时时间不共用一条坐标轴。
- 引用他人的数字时，保留原文的实验条件；条件缺失时注明「原文未说明」。

## 确定程度用词

| 证据状态 | 推荐用词 | 避免 |
| --- | --- | --- |
| 实测且可复现 | 实测表明、测得、已验证 | 无 |
| 源码确认 | 按当前实现（路径@commit）、源码中 | 一定、永远 |
| 估算 | 估算、理论上限、预计 | 达到、实现了 |
| 设计意图 | 按设计、计划、预计 | 已经、实现了、完全 |
| 有部分证据 | 很可能、主要原因之一，并附证据 | 就是、根本原因 |
| 没有证据的推测 | 候选原因、假设、待验证 | 把「应该是」改写成确定句 |

## 性能数字的必备上下文

报告中第一次出现某组性能数字时，在测量设置章节或表注中给出以下信息；后文引用同一组数字时可以省略：

- 硬件：GPU 型号与数量、互联方式；需要时写功耗上限和时钟设置。
- 软件：驱动、CUDA、编译器、框架或仓库版本（commit）、关键环境变量。
- workload：shape、dtype、batch 组成、序列长度分布、causal 或 varlen 等语义开关。
- 方法：warmup 次数、重复次数、计时方式（CUDA events、nsys、ncu、wall clock）、是否清空 L2、是否包含 launch 和 host 开销、launch 方式（是否在 CUDA Graph 中、是否启用 PDL）。
- 统计：中位数或均值，离散程度（min/max、p99 或标准差），运行次数。

工具差异会改变数字的含义：

- ncu 默认锁定时钟（`--clock-control base`），并串行执行被 profile 的 kernel；metric 需要多个 pass 时会重放 kernel，且默认在每个 pass 前刷新缓存（`--cache-control all`），L2 处于冷状态。因此 ncu 的 duration 不等于线上耗时，线上耗时和占比以 nsys、框架 profiler 或 benchmark 为准。
- ncu 串行化 kernel 后，PDL 和多 stream 之间的重叠不再存在；评估这类重叠使用 nsys 或 benchmark。
- 冷 L2 和热 L2 的结果可能差别很大，说明测量时 L2 的状态。
- 端到端指标需要说明是否包含 tokenizer、调度、网络等非 GPU 部分。

## 加速比与百分比

- 加速比等于基线耗时除以新耗时，写作 `1.5×` 或 `1.5 倍`，同一文档统一一种。
- 每个加速比写明基线：名称、版本、配置，并确认在同一环境和同一 shape 下测得。
- 「提升 50%」需要说明是吞吐提升还是耗时降低。加速 1.5× 等于吞吐提升 50%，也等于耗时降低约 33%。
- 百分比与百分点分开：利用率从 40% 到 60% 是增加 20 个百分点，相对增加 50%。
- 多个 shape 的汇总结果写明汇总方式（几何平均、加权平均或范围），并给出最小值和最大值。
- 由原文数字可以直接算出的量，计算错误时可以修正，并在说明中指出；不能补造原文没有的基数。

## 峰值与利用率

- 写明峰值的口径：标称峰值（官方资料）或可达峰值（microbenchmark 实测）；dense 或 sparse；对应的 dtype；对应的时钟。
- 利用率写作 `为 BF16 dense 标称峰值的 53%（峰值取自〔来源〕）`，不只写「算力利用率 53%」。
- 硬件参数从用户数据、本地参考 skill（如 `cuda-skill`、`nv-gpu-kernel-performance-modeling`）或官方资料获取，并注明来源；不凭记忆填写。
- occupancy 是 active warp 与最大 warp 数之比，不是 SM 利用率。两者需要分开报告。

## 单位

- 时间：`ns`、`µs`、`ms`、`s`。同一文档中 `µs` 与 `us` 统一一种。
- 计算量用 FLOP，吞吐用 FLOP/s；`TFLOPS` 表示每秒 10^12 次浮点运算。不写 `TFlops`、`Tflops`。
- 存储：`GB` 表示 10^9 B，`GiB` 表示 2^30 B。厂商资料常把二进制容量写成 KB、GB；需要精确计算（SMEM 预算、显存账本）时使用 KiB、GiB 并注明换算。
- 带宽写 `GB/s`、`TB/s`，并说明是单向还是双向（互联带宽尤其需要）。
- 推理指标：TTFT、TPOT、ITL、端到端延迟、tokens/s。写明统计分位（p50、p99）、并发数和是否为单请求。
- 训练指标：tokens/s/GPU 与集群总吞吐分开；MFU 写明计算量公式和峰值口径。

## 表格

- 列标题带单位，例如「耗时（µs）」「带宽（TB/s）」。
- 同一列保持相同的有效位数，数字右对齐。
- 基线放在第一数据列；加速比列写明「相对 <基线>」。
- 实测和估算分列或分表，并在表注中写明证据等级和测量条件。
- 大表放附录或链接到 CSV，正文只保留支撑结论的行。

## 估算的写法

估算按「公式 → 参数取值 → 结果 → 与实测的差距」组织：

1. 写出公式并定义每个符号和单位。
2. 给出参数取值及来源，包括峰值口径。
3. 给出结果，并标注「估算」。
4. 有实测数据时，给出实测与估算的比值，并解释差距的候选原因。

不要把估算结果放进实测结果表，也不要用估算结果支撑「已达到」类结论。

## 回归样例

以下样例用于检查 GPU 技术报告中的事实保真、证据等级和口径。改写后不得增加样例原文没有的数字或条件；缺失信息用「待补充」「待确认」标出。

### 性能结论

#### 样例 G1

改写前：

`这个 kernel 性能提升了很多，基本打满了带宽。`

改写后：

`优化后该 kernel 的耗时从〔待补充〕降至〔待补充〕〔测量方式、GPU、shape 待确认〕。带宽达成比例为〔待补充〕〔带宽类型（DRAM、L2 等）与峰值口径待确认〕。`

检查点：没有补造数字，也没有替原文选定带宽类型；「基本打满」改为可核对的达成比例。

#### 样例 G2

改写前：

`采用 warp specialization 后，访存延迟被完全掩盖。`

改写后：

`采用 warp specialization 后，访存与计算按设计可以重叠（设计）。访存延迟是否被完全掩盖尚无时间线证据，待 IKET 或 nsys 确认。`

检查点：保留设计意图并标注为「设计」；「完全掩盖」降级为待验证，并指出需要的证据。

#### 样例 G3

改写前：

`新实现比 FA3 快 1.3x。`

改写后：

`新实现相对 FlashAttention-3〔版本待确认〕加速 1.3×〔GPU、shape、dtype 待确认〕。`

检查点：保留 1.3；补全官方名称；基线版本和测量条件标记待确认。

#### 样例 G4

改写前：

`耗时从 1.2 ms 降到 0.8 ms，性能提升 50%，耗时降低 50%。`

改写后：

`耗时从 1.2 ms 降至 0.8 ms，即加速 1.5×，耗时降低约 33%。原文中「耗时降低 50%」与给出的数字不一致，已按原数字修正。`

检查点：由原文数字可以直接算出的量可以修正，并说明修正原因。

### 指标与口径

#### 样例 G5

改写前：

`occupancy 只有 12%，所以 SM 利用率很低，需要提高 occupancy。`

改写后：

`occupancy 为 12%〔理论值或实测值待确认〕。occupancy 低不等于 SM 利用率低，例如 warp-specialized kernel 常以较低 occupancy 换取更多寄存器。是否存在发射空泡，需结合 issue 活跃度和 warp stall 采样判断。`

检查点：保留 12%；拆开错误的因果关系；用「例如」引入通用背景，没有断言本 kernel 属于哪一类；不直接给出「提高 occupancy」的结论。

#### 样例 G6

改写前：

`这个 GEMM 跑到了 1200 TFlops，算力利用率 53%。`

改写后：

`该 GEMM 实测吞吐为 1200 TFLOPS，为峰值的 53%〔峰值口径待确认：dtype、dense 或 sparse、标称或可达〕。`

检查点：统一 TFLOPS 写法；利用率的分母必须写明，不自行假设 dense 或某种 dtype。

#### 样例 G7

改写前：

`ncu 测得 kernel 耗时 85 us，所以线上每个 decode step 这个 kernel 占 85 us。`

改写后：

`ncu 测得该 kernel 的 duration 为 85 µs〔本次采集的时钟与缓存设置待确认〕。ncu 默认锁定时钟并在每个 pass 前刷新缓存，这一数值不能直接等同于线上耗时；线上耗时以 nsys 或框架 profiler 的测量为准。`

检查点：保留 85；补充的是工具的默认行为，本次是否使用默认设置标为待确认；推论被降级。

#### 样例 G8

改写前：

`按 roofline 这个 kernel 能到 3.2 TB/s，实际跑到 2.9 TB/s，带宽利用率 90%。`

改写后：

`按 roofline 估算，该 kernel 的带宽上限为 3.2 TB/s〔峰值来源待补充〕。实测达成 2.9 TB/s，约为估算上限的 90%。`

检查点：估算与实测分开写；明确 90% 的分母是估算上限。

### 原因与机制

#### 样例 G9

改写前：

`训练和推理的 logprob 对不上，应该是 attention kernel 不一样导致的。`

改写后：

`推理侧（rollout）与训练侧重算的 log-prob 存在偏差〔偏差指标与数值待补充〕。两侧 attention kernel 实现不同是候选原因之一，尚未通过控制变量实验确认。`

检查点：「应该是」保留为候选原因，没有升级为结论。

#### 样例 G10

改写前：

`SGLang 用 radix tree 管理 KV cache，命中率很高。`

改写后：

`SGLang 使用 radix tree 管理可复用的 KV cache 前缀〔源码路径与 commit 待补充〕。命中率取决于请求之间的前缀复用程度，需要给出具体 workload 下的实测命中率。`

检查点：源码说法需要路径和 commit，路径从源码核对后填写，不凭记忆补全；「命中率很高」改为依赖条件的表述，没有补造数值。

#### 样例 G11

改写前：

`我们的方案零开销地实现了通信计算重叠。`

改写后：

`本方案让通信与计算重叠执行。重叠后的额外开销为〔待补充〕〔测量条件待确认〕。`

检查点：原文的重叠主张保留；「零开销」需要实测支持，没有证据时改为待补充的数值。

### 整理模式

#### 样例 G12

改写前（截图原文）：

`decode 阶段 batch 小，所以用 split-KV。`

改写后：

`decode 阶段 batch 小，所以用 split-KV。〔补充〕decode 阶段每个请求通常只有 1 个 query token，按 batch 和 head 划分得到的 CTA 数可能少于 SM 数；沿 KV 长度切分可以增加并行度，代价是额外的归约。`

检查点：原文保留不动；新增解释标注「补充」，没有改写原文的因果关系。
