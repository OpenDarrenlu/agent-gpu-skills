# 实验报告结构

仅在撰写、改写或审阅实验报告时读取本文件。实验报告包括 A/B、消融、参数 sweep、端到端压测、调优确认、回归确认和 sanity check。它回答「这次实际测了什么、结果是否回答了原问题、证据能推到多远」；技术原理报告回答「机制是什么」。一份工作同时有机制解释和实验时，按读者的主要问题选主骨架：以机制为主时用 [报告结构模板](gpu-report-structures.md) 中的对应类型，实验部分按本文规则写；以实验结论为主时用本文的模板，机制解释放进「消融与机制」一节。

头部元信息、结论摘要、附录等通用约定，以及 [证据与数字规范](evidence-and-numbers.md) 中的证据等级、性能数字上下文和加速比写法，在实验报告中同样适用。本文只补充实验报告特有的部分。

## 选择篇幅

| 情况 | 用什么 | 起点 |
| --- | --- | --- |
| 比较、证据和决策能用一张小表加几段话说清，例如少数几组运行的 A/B、sanity check 或回归确认，也可以附带一个小的对照或一次失败后的重跑 | 短报告 | [assets/experiment-report-short.md](../assets/experiment-report-short.md) |
| 比较本身、证据链或决策需要更多篇幅，例如多阶段或多基线的比较、要靠消融支撑机制结论、要逐项交代运行身份与覆盖、要逐条对照判定规则 | 完整报告 | [assets/experiment-report-full.md](../assets/experiment-report-full.md) |
| 沿一至两个变量轴扫描，例如并发、batch、序列长度、split 数或 tile | 按规模选短报告或完整报告，结果部分按本文「参数 sweep」一节组织 | 同上 |

模板只是起点。删除不适用的章节，不为凑齐章节补造内容。篇幅按比较、证据和决策的需要选择，不按运行数或对照数机械决定：短报告可以简要交代一次失败后的重跑、一个被排除的运行或一个小的附加对照。这些内容在短报告中写不清，或者读者需要完整报告中的某几节才能判断结论时，再改用完整报告，并只保留需要的章节。

## 把执行状态、结论判定和各项结果分开

三类状态互相独立，分别写：

- **执行状态**：按预设的协议和覆盖范围说明运行做到了哪一步，与正确性结果和假设是否成立无关。「完成」指协议规定的运行和检查都执行到了协议规定的终点；协议事先写明的预期失败被记录下来，或约定的提前停止条件被触发（例如正确性门槛未通过即不再测性能），也属于完成，不要求每个运行都产出性能指标。「部分完成」指有缺测或中途偏离协议，但至少一组计划中的比较可以成立；协议允许时，部分完成的结果可以支持限定了范围的结论，范围要写明。「失败」指因基础设施、环境或执行问题，没有任何计划中的比较可以成立。基础设施失败与工程或科学上的负结果分开写：后者是完成的实验得到了否定的结论。
- **结论判定**：按预设判定规则给出「支持」「否定」或「无法判定」。结果清楚地否定了假设、且协议已执行完时，写「执行：完成；判定：否定」，而不是「失败」。负结果也是完成的实验。
- **各项结果**：正确性（通过、失败、未测）、实现状态（已实现、已接线、未接线、已提交、未提交）和目标达成（达到、未达到、无预设目标）分开报告。数值正确不代表达到性能目标；达到性能目标也不代表改动已经提交或在生产路径中生效。

以下情况判定为「无法判定」，并写明原因：结果落在支持与否定的阈值之间；主比较缺少一侧；重复次数少于判定规则的要求；运行身份未经核实，或两臂之间存在未受控的差异，使结果无法归因到要比较的变量；没有预设判定规则。

两臂的 commit、未提交改动或镜像不同，本身不导致无法判定：A/B 的实验组往往正是通过这些差异实现被测变量。要求是核实每一臂实际运行的身份，并逐项交代被测变量之外的其他差异及其影响。附有可识别 diff 的未提交改动是有效的运行证据。

用户、设计文档或上游验收清单给出的目标、容差和 SLA，原样冻结并注明来源，看到结果后不再调整。没有预设标准时，写「无预设验收标准」，只报告观测值和比较结果，不自行设定通过线。

## 写清比较的问题

先说明这次比较要回答哪个问题。不同问题的数字不能放在同一列，也不能互相换算。

- **固定代码或配置的 A/B**：两臂只差被测变量，其余部署参数、并行方式和 workload 全部固定。它回答「这个改动本身带来多少变化」。
- **各自最优的有效配置**：每一侧调到自己最好的有效配置后再比较。它回答「在各自最好的情况下谁更快」，需要逐点列出两侧不同的配置。
- **同一并发点的比较**与**各自最大吞吐点的比较**也是两个问题，写明属于哪一种。

基线的身份要贯穿全文。历史背景基线、调优前基线、参考实现和最终生产基线是不同的比较对象。每个加速比写明对应哪一个基线；后续阶段换了基线，就新开一列或一节，不与前一阶段的数字相除。

多个改动合在一起测得的收益，不能拆成各项收益之和。要报告单项贡献，需要只改该项的对照。

## 绑定实际运行身份

每个主要结果都要能追溯到产生它的那次运行。按需记录以下字段：

| 字段 | 记录什么 |
| --- | --- |
| 源码 | commit；有未提交改动时给出 diff 或其哈希。需要时还要分开记录源码、安装的 wheel、实际加载的库和 JIT 特化版本 |
| 运行 | 运行或 arm 标识、日期、执行顺序 |
| 硬件与拓扑 | GPU 型号与数量、互联、节点数、资源放置 |
| 软件 | 镜像、驱动、CUDA、框架版本、关键环境变量 |
| workload | kernel 写 shape、dtype 和分派分支；serving 写请求分布；训练写数据、长度分布和 batch |
| 命令与配置 | 实际执行的命令，以及解析后的最终配置 |
| 计时与汇总 | 计时层级、计时方式、重复次数和汇总公式 |
| 原始产物 | 日志、JSON、trace 或 profile 文件的路径或 ID |

计划中的配置不是运行证据。实际生效的配置要从启动日志、运行时输出、kernel 名或 dispatch 记录中核对。字段缺失时写「未记录」或「未验证」，并在范围限制中说明影响，不要从设计文档补填。实测时使用的运行环境与最终交付的镜像或分支不同时，写明差异和尚缺的验证，不直接沿用实测结论。

## 计时层级与公平对照

### 计时层级

单个 kernel、layer 或模块、一次 forward 或 decode step、rollout 或生成阶段、完整训练 step、端到端 serving 吞吐，是不同层级的数字。报告写明每个数字属于哪一层，不跨层换算。局部加速不等于端到端加速；两者差距明显时，说明其余阶段为什么不受影响（例如该阶段不受 GPU kernel 约束），并标注证据等级。

重叠执行的 kernel，其耗时相加不等于墙钟时间。按 trace 归因时，说明是按 kernel 耗时还是按墙钟区间统计。

### 计时口径

- 说明是否在 CUDA Graph 中、是否包含 warmup 和冷启动、L2 或 cache 是冷是热。
- profiler 下的耗时用于归因，与不开 profiler 的验收计时分开报告。profiler 的时钟控制、缓存刷新、kernel 重放和采集范围都可以配置，不同运行的设置可能不同。引用 profiler 数字时记录实际使用的设置，例如 ncu 的 `--clock-control`、`--cache-control` 和 replay 模式，nsys 的采集选项，不要假定每次运行都用了相同的默认值。
- 稳态吞吐与包含启动、排空阶段的整段平均分开报告。

### 公平对照

- 避免两臂之间的资源干扰：优先在同型号硬件上、没有跨臂争用的条件下运行，例如串行或成对执行，或使用互不共享资源的 GPU。多个变体并发运行时，确认它们不共享会影响结果的资源，例如同一张卡、同一节点的互联或主机资源。
- 共享资源是有意安排的（例如争用实验本身），或者无法避免时，记录实际的资源隔离方式和运行期间的负载，并在局限中写明它对结论的影响。
- 条件允许时交替顺序或反转顺序（AB / BA）。重复方式按实验选择，例如独立进程重启或同一会话内的成对运行，并写明用的是哪一种。
- 报告重复次数、每对的数值和离散程度，以及无效或被排除的运行及其原因。
- 写明汇总公式和权重，例如几何平均、按 token 加权，或先取分位数再求平均（后者不是全局分位数）。
- 调优选点与调优后确认是两轮。用筛选轮选出配置，用独立的确认轮报告最终数字；不要用选点的那批数据报告收益。

### 统计

本文不规定固定的重复次数、阈值或 p 值。按实验设计和用户给定的协议执行，并遵守以下原则：

- 同一运行内连续的计时样本互相相关，不能当作独立样本做检验。
- ML 实验中的不同 seed，不自动等于独立的 GPU 计时样本。
- 只有一次运行时，写明「无独立重复，未做统计检验」，不给区间或 p 值。
- 只有汇总值时分两种情况。来源给出了区间或检验结果，并说明了所依据的独立重复和计算方法：保留这些统计结果，注明来源和方法，并写明无法从原始数据复核。只有一个无法追溯的汇总数字：按单个观测值报告，不补算区间或 p 值。
- 差异小于同一代码跨轮运行的波动时，写「未超出波动」，不作为收益报告。

## 机制与因果边界

- 组合实现或局部加速不能隔离单一机制的作用。声称某个机制贡献了多少，需要只改该机制的对照或消融。
- 计数器的变化只能说明与补丁有关联。profiler 中的等待点只说明谁在等，不说明对方为什么慢。
- 有限的数值测试矩阵是工程验收，能发现不等价，但不能证明在全部输入上等价；可以直接论证的数学恒等属于另一类证据，两者分开写。
- 提出的优化、ncu 的预估加速和理论上界都不是实测收益，写成「预计」「上界」。
- 解释超出数据时标注「推断」或「待确认」，并列出替代解释和能区分它们的最小实验。

## 按方向补充

以下各项在相关时补充，不要求每份报告全部写到。

### kernel、算子与量化

- shape 和 dispatch 矩阵要有代表性：覆盖实际会进入的分派分支，以及 tail、空输入、跨 page 边界等边界情况。
- 写明 scale 粒度、格式转换和累加精度的语义。
- 参考实现：说明参考值怎样构造、容差从哪里来、覆盖了哪些数值情形。
- 运行时 dispatch 证明：用日志、kernel 名或计数器说明实际走了新路径。
- 各臂是否重新调过 split、tile 或 graph 配置会改变比较的含义，要写明是固定配置还是各自选优。
- 源码、编译产物和实测三类证据分开写。

### serving 与推理压测

- workload 类型：定长合成负载（例如固定长度并忽略 EOS）与自然停止的真实多轮负载结论可能不同，要分开报告。写明 prompt 和输出长度分布、完成的输出数、失败数和截断数。
- 并发：标称会话数或并发上限与实测在飞并发分开写；per-user 指标写明分母。
- 吞吐：整段平均、稳态吞吐和 per-user 吞吐分开写；说明是否计入命中 prefix cache 的 token。
- 延迟：TTFT、TPOT、ITL 写明分位数和单位。
- cache：写明 prefix cache 是否开启，以及档间是否重置；测到时报告 KV 容量、饱和和 preemption。
- 投机解码：区分真实接受和模拟接受；写明接受长度的计数约定，例如是否包含目标模型必然产出的那个 token。
- 不同压测工具或口径的结果并列给出，写一张口径对照表说明差异，不互相换算。

### 训推一致、MoE、训练与通信

- 覆盖范围：proxy 与完整模型在特性、层数、并行拓扑上的差异；未覆盖的路径列出来。
- 被比较的路径：训练侧实际使用的、带梯度的前向，与不带梯度的重算打分是两条路径，写明比较的是哪一条。
- 指标：写明 mask、有效 token 数和聚合方式；目标是 logprob 差、逐位一致还是容差内一致，按预设目标写。
- 检查范围：前向、反向、参数更新和质量检查按适用范围分别报告。只做了推理侧验证时，不要写成训练侧也已验证。
- 配置：dtype 与量化方式，TP、EP、CP、SP、PP 和资源放置；与生产布局不同的地方要写出来。

## 参数 sweep

- 共享配置只列影响解读的项，以及偏离默认值的项；变化轴单独说明。
- 每类指标一张表，行是轴的取值。两个轴时用二维布局；有条件变量时作为附加列，让轴的作用一眼可见。
- 观察写轴的规律，而不是逐个复述数值：单调趋势、轴之间的交互、拐点、对指标没有影响的轴。没有影响也是有用的结论。
- 轴上的 workload 发生漂移时要写明，例如每一档使用的请求集合不同，导致长度分布随档位变化。
- 计划中未跑的点保留行，标「未跑」，并写明原因。

## 图表与正文组织

- 图和表写明单位、分母、基线和数据来源。一张小表能说清时，不必画图。
- 正文按读者的问题组织。探索过程和中间尝试放附录或证据索引；失败和回退的候选在「局限、负结果与替代解释」中简要说明。
- 被后续证据纠正的结论，列出旧说法、纠正它的证据和原因，不悄悄删除。

## 实验报告最终检查

- 执行状态、结论判定和各项结果是否分开写
- 判定规则和验收标准是否来自预设来源；没有时是否写明「无预设验收标准」
- 比较问题是固定配置 A/B 还是各自最优配置；每个加速比是否写明对应哪一个基线
- 每个主要结果是否绑定了源码身份、运行、环境、workload、命令、计时方式和原始产物
- 计划与实际运行是否对照；缺测、作废和排除的运行是否保留并写明原因
- 计时层级是否写明；profiler 耗时是否与验收计时分开；不同层级和口径是否被互相换算
- 重复次数、离散程度和汇总公式是否写明；统计结论是否建立在独立样本上
- 机制结论是否有单项对照；关联、推断和预估是否被写成了因果或实测收益
- 负结果、失败路径和最小的后续实验是否保留
