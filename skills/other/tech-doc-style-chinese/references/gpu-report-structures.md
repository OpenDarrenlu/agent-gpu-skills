# 技术原理报告结构模板

仅在撰写或审阅 GPU 算子、推理框架、训练框架方向的技术原理报告时读取本文件。骨架只是起点：删除不适用的章节，不要为了套模板补造内容。资料不足的位置写「〔待补充〕」或「〔待确认〕」。骨架中的 `<…>` 是填写提示，交付前全部替换或删除。

## 通用约定

### 头部元信息

每份报告在标题下给出元信息块，让读者在阅读正文前知道结论的适用范围和时效。各类模板按需选用以下字段，名称可以按报告类型调整（例如性能报告写「对象」）：

- 状态：提案、实现中、已实现、已验证。状态决定正文时态，提案中的行为用「计划」「预计」，已观测的行为用「实测」「已验证」。
- 范围：支持的 shape 范围、dtype、前向或反向、是否支持 causal、varlen、paged KV 等；同时写明不支持的情况。
- 环境：GPU 型号与架构、驱动与 CUDA 版本、框架或仓库版本（commit）；kernel 报告还写目标架构特性（如 `sm_90a`、`sm_100a`）和 launch 方式（是否在 CUDA Graph 中、是否启用 PDL）。
- 证据日期：最后一次核对源码和测量结果的日期。

### 结论摘要

正文第一节固定为「结论摘要」，用 3 至 5 句回答：要解决什么问题，用了什么方法，关键数字是多少（带条件和基线），结论是什么，主要局限是什么。读者只读这一节也能做出判断。

### 附录

探索过程、失败尝试、完整数据表和原始日志放附录或链接，不放进正文主线。被否决的方案在「取舍与备选方案」中用一两句说明否决原因。

## 1. 算子/kernel 原理与设计报告

适用于：新算子设计提案、已实现 kernel 的原理说明、PR 设计说明、kernel 移植（Hopper 到 Blackwell、CUDA 到 Triton 或 TileLang）说明。

读者要带走：算子算什么，工作如何划分到 CTA 和 warp，数据如何在存储层级之间流动，为什么这样设计更快，数值是否正确，哪些情况不适用。

```markdown
# <算子名>：<一句话说明设计要点>

> 状态：提案 | 实现中 | 已实现 | 已验证
> 范围：<shape 范围、dtype、前向/反向、causal/varlen；不支持的情况>
> 目标：<GPU 与架构（如 sm_100a）、CUDA/编译器版本、实现方式（CUDA/CuTe DSL/Triton/TileLang）、launch 方式（CUDA Graph/PDL）>
> 证据日期：<YYYY-MM-DD>；代码：<仓库@commit>

## 结论摘要

## 1. 算子语义
- 数学定义、输入输出 shape/dtype/stride/layout、是否原地修改
- 参考实现与容差
- 计算量、访存量与算术强度（估算），roofline 位置

## 2. 设计
### 2.1 并行划分：grid → cluster → CTA → warp group/warp → thread
### 2.2 数据搬运与存储层级：HBM → L2 → SMEM → 寄存器/TMEM
### 2.3 计算：MMA 指令与形状、累加精度、非 MMA 部分（softmax、归约、量化）
### 2.4 流水线与同步：stage 数、生产者/消费者角色、mbarrier、buffer 复用条件
### 2.5 调度：非 persistent / static persistent / 动态（CLC）/ Stream-K；负载均衡与尾效
### 2.6 边界与特化：tail、mask、varlen、按 shape 分派

## 3. 资源与编译结果
寄存器、SMEM、spill、理论 occupancy（编译产物）

## 4. 数值正确性
对比对象、容差、累加顺序、run-to-run 确定性、训推一致要求

## 5. 性能
测试矩阵、结果表（实测）、相对基线、达成峰值比例与峰值口径、实测与估算的差距及原因

## 6. 取舍与备选方案

## 7. 局限、风险与后续

## 附录：复现步骤、原始数据
```

必答问题：

- 算子在模型中的位置和典型 shape 是什么（prefill、decode、训练前向、训练反向）？
- 理论上受限于什么（compute-bound、memory-bound 或 latency-bound），依据哪项估算？
- 每个 CTA 和 warp 负责哪块数据，为什么这样划分？
- 每个 buffer 由谁生产、由谁消费，何时可以复用，在哪里同步？
- 实测与估算差多少，差距来自哪里？
- 与参考实现的数值差多少，是否 run-to-run 确定？
- 哪些 shape 或配置会退化或不支持？

常见问题：

- 把设计意图写成已观测行为，例如没有时间线证据就写「TMA 加载与 MMA 完全重叠」。
- 只报告最好的 shape，回避退化区间。
- 堆砌「warp specialization、TMA、swizzle」等技术名词，不说明每项解决什么问题。

## 2. 性能分析与优化报告

读者要带走：瓶颈是什么，哪几个指标值支撑这一判断，下一步按什么顺序优化，每项预期收益多少。

```markdown
> 日期：<YYYY-MM-DD>

## 2. 头部指标

## 6. 置信度与未覆盖问题

## 7. 复现
```

必答问题：

- 结论依据哪几个 metric 的具体值？
- 该 kernel 占端到端耗时的比例是多少（来自 nsys 或框架 profiler）？
- 采集时时钟是否锁定？duration 能否直接对比线上耗时？
- 测量用的 shape 是否代表真实 workload 的分布？
- 优化前后的对比是否在同一环境、同一 shape 下完成？

常见问题：

- 只写「是 memory-bound」，不给数值。
- 把 ncu 锁频条件下的 duration 当成线上耗时。
- 优化建议超过 5 条且不排序。
- 只看全程平均值，不看 PM sampling 时间线，漏掉尾效。

```markdown
## 7. 边界条件、已知问题与相关 PR/issue
```

必答问题：

- 机制对哪类 workload 有效（前缀复用率、输入输出长度、并发数）？
- 与 CUDA Graph、chunked prefill、speculative decoding、PD 分离等机制如何交互？
- 默认值和行为在哪个版本引入或变化？
- 性能数字来自离线吞吐测试还是在线 SLO 测试，负载如何构造？

常见问题：

- 源码走读变成逐行翻译，读者看不出主线。
- 不注明 commit，报告很快过期且无法核对。
- 把官方博客的宣传数字当成本环境的实测结果。

显存账本必须写明口径。例如 ZeRO 论文对混合精度 Adam 按每个参数 16 B 计（引用）：16 位参数 2 B、16 位梯度 2 B、FP32 主权重与两份 Adam 状态共 12 B。不同框架的实际组成不同，例如梯度以 FP32 保存时会更多，以所用框架的源码和配置为准；以上都不含激活、通信 buffer 和碎片。

必答问题：

- 每个角色在哪些 GPU 上运行，何时占用、何时释放显存？
- 权重同步采用什么方式，耗时多少？
- 各并行维度的乘积与 GPU 总数是什么关系？

- 吞吐不说明单位：tokens/s/GPU 与集群总吞吐混用。
- rollout 生成吞吐与训练吞吐混在同一个数字里。

## 5. 训推一致与数值一致性分析报告

适用于：rollout 与训练重算 log-prob 偏差、bitwise 一致性、run-to-run 确定性、batch invariance、低精度量化误差、跨后端数值差异等问题的分析。

读者要带走：差异有多大，比较的是哪两个量，差异来自哪里，哪些原因已确认，修复的代价是什么。

目标是 bitwise 0 diff（true on-policy）并按 `train-inference-consistency` 的 C0–C10 流程推进时，交付报告的字段以该 skill 的 `workflow/report-template.md` 为准，本模板用于组织中文分析报告。

```markdown
# <模型或场景> 训推一致性分析：<一句话结论>

> 训练侧：<引擎、版本、dtype、kernel 后端>
> 推理侧：<引擎、版本、dtype、attention backend、batch 设置>
> 一致性目标：bitwise 一致 | 容差内一致（阈值）| 统计一致（指标分布）
> 证据日期：<YYYY-MM-DD>

## 结论摘要

## 1. 现象与度量
比较哪两个量、指标定义、数值、随 step/序列长度的变化
指标示例：逐 token |Δlog-prob| 的最大值与分布、KL、重要性采样比的分布

## 2. 对比口径
dtype、logits 精度、temperature 是否在 log_softmax 之前应用、top-p/top-k 截断、tokenizer、padding、MoE 路由

## 3. 差异来源分解

## 4. 控制变量实验
| 实验 | 变更 | 结果 | 结论 |

## 5. 修复或缓解方案及性能代价

## 6. 剩余差异与风险

## 7. 复现
```

必答问题：

- 目标是哪一级一致性：bitwise 一致、容差内一致还是统计一致？
- 差异是否随序列长度、batch 组成或训练 step 增长？
- 每个原因是否经过控制变量实验确认？
- 修复方案的性能代价是多少？
- 观测到的差异中，多少来自数值实现，多少来自异步训练的策略滞后？

常见问题：

- 把「应该是 kernel 不同导致的」写成确定原因。
- 混用 run-to-run 确定性与训推 bitwise 一致。
- 只给均值，不给最大值和分布。
