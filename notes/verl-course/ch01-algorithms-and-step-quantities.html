结论摘要

verl 把一个 RL step 拆成「生成 → 打分 → 三次无梯度前向（old、ref、value）→ driver 上算优势 → 带梯度更新 → 权重同步」，每一段只向 TransferQueue 写入若干字段；弄清每个字段由谁、在哪个参数版本下算出，是读懂后续所有章节的前提。源码 所有优势估计器只消费 token_level_rewards、response_mask 和分组键 uid（GAE 额外消费 values），在 driver 进程上用无梯度张量计算；整个 step 中唯一带梯度的量是 actor 训练前向产生的 log_prob，它同时进入 policy loss、entropy loss 和 KL loss。源码 KL 有两条路径：algorithm.use_kl_in_reward 在 driver 上用 old_log_probs 扣减奖励，actor.use_kl_loss 在 worker 上用带梯度的 log_prob 进入 loss（默认 low_var_kl，即 k3）。loss 以整个 mini-batch 在 DP 组内 all-reduce 后的全局 token 数（或序列数）归一化，因此梯度与 micro-batch 切分无关，但 loss_agg_mode 的选择会改变长短回复的相对权重。主要局限：本章只覆盖默认 V1 sync 路径和最常用的估计器；异步模式下 old_log_probs 的含义会变化，留到第 6、8 章。

1. LLM 生成如何写成 RL 记号

把一次生成看作 token 级的马尔可夫决策过程：状态 s_t = (x, y_<t) 是 prompt 加上已生成的前缀，动作 a_t = y_t 是下一个 token，策略是带温度的 softmax：

π_θ(y_t | x, y_<t) = softmax(logits_t / T)[y_t]　　T = actor_rollout_ref.rollout.temperature

一条轨迹就是一条回复。数学推理、代码等 RLVR（可验证奖励）任务只在回复结束后给一个标量奖励 R（outcome reward）。verl 把这个标量放在回复的最后一个 token 上，其他位置为 0，得到形状与回复相同的 rm_scores，进入优势计算时改名为 token_level_scores。源码 experimental/agent_loop/agent_loop.py L143–148

多轮工具调用时，回复中夹着工具返回的 observation token。这些 token 由环境产生，不是策略的动作，因此 response_mask 在这些位置为 0。后文所有估计器和 loss 都只在 response_mask = 1 的位置计入；GAE 与 REINFORCE++ 递推时还会「跳过」mask 为 0 的位置，把下一步的值原样带过去。源码 core_algos.py L254–256、L722–726

进入 driver 计算优势时，这些字段被 to_padded_tensor() 转成形状 [N, T_r] 的稠密张量：N 是本次参与计算的轨迹条数（单轮时等于 prompt 数 × rollout.n），T_r 是本批最长回复的长度。TransferQueue 里存的是不带 padding 的 nested tensor。源码 v1/trainer_base.py L1744–1751

分组键 uid 在 driver 从 dataloader 取 prompt 时用 uuid4 生成，同一个 prompt 的 n 条采样共享同一个 uid。GRPO、RLOO 的「组」就是按 uid 划分的。源码 v1/trainer_base.py::_fetch_one_gen_batch L1477

2. PPO clip 与 dual-clip 在代码里长什么样

2.1 从 REINFORCE 到 clipped surrogate

策略梯度的基本形式是 REINFORCE：用当前策略采样，再按优势加权对数概率的梯度。

∇J(θ) = E_{a~π_θ} [ Σ_t ∇ log π_θ(a_t|s_t) · Â_t ]

一次 rollout 的样本要被多个 mini-batch、多个 epoch 复用，从第二次梯度更新起，样本就不再来自当前策略。PPO 用重要性比率 r_t 修正分布差异，并把比率裁剪在 [1−ε_low, 1+ε_high] 内，限制单次更新的步幅：

r_t(θ) = π_θ(a_t|s_t) / π_old(a_t|s_t) L_clip(θ) = −E_t [ min( r_t·Â_t , clip(r_t, 1−ε_low, 1+ε_high)·Â_t ) ]

Â < 0 时，标准 clip 对 r_t 增大没有上限：某个 token 的概率被意外推高后，loss 会随 r_t 线性增长。dual-clip 再加一层上限 −c·Â_t（c = clip_ratio_c，默认 3.0）：

Â_t < 0 时：L_t = min( max(−r_t·Â_t, −clip(r_t)·Â_t), −c·Â_t )

2.3 其他 policy loss 的差异点

所有 policy loss 通过 @register_policy_loss(name) 注册，由 actor_rollout_ref.actor.policy_loss.loss_mode 选择，签名统一为 (old_log_prob, log_prob, advantages, response_mask, loss_agg_mode, config, rollout_is_weights)。源码 core_algos.py L53、L70；losses.py L113–126 两个常用变体的差异如下：

  • GSPO：把比率换成序列级几何平均 s_i = exp(mean_t log r_{i,t})，再用 log_prob − log_prob.detach() + sg(log s_i) 让梯度仍按 token 回传。裁剪对象从单个 token 变为整条序列。源码 L1578–1597
  • CISPO：loss 写成 −sg(clip(r))·Â·log π_θ。裁剪只限制权重大小，不切断梯度；PPO 中被 clip 的 token 完全不贡献梯度，CISPO 中仍然贡献。源码 L2079–2084

3. 四种优势估计器：基线从哪里来

优势 Â_t 回答「这个动作比平均水平好多少」。不同估计器的区别集中在一点：平均水平（基线）从哪里来、在什么范围内归一化。verl 的所有估计器共享同一个接口：输入 token_level_rewards、response_mask，按需输入 index（即 uid）、values、config，输出形状均为 [N, T_r] 的 (advantages, returns)，全程在 torch.no_grad() 下计算。

分派逻辑在 ray_trainer.py::compute_advantage：GAE 与 GRPO 走显式分支，其他估计器从 @register_adv_est 注册表取函数，并且只有当 batch 中存在 uid 时才传 index。源码 ray_trainer.py L187–282；core_algos.py L116 V1 trainer 在外面再包一层 compute_advantage_for_multi_trajectories，第 7 章讲 agent loop 时回到这一层。v1/utils.py L148

3.2 GRPO：同一 prompt 的 n 条回复互为基线

实现细节有三处值得记住。第一，std 用的是 torch.std，即无偏估计（除以 n−1）。第二，组内只有 1 条时均值取 0、标准差取 1，优势等于原始奖励。第三，algorithm.norm_adv_by_std_in_grpo=False 时不除标准差，即 Dr.GRPO 的做法。源码 core_algos.py::compute_grpo_outcome_advantage L304–331 该实现是逐样本的 Python 循环，大 batch 时可以换成 grpo_vectorized。

代码直接用等号右侧的形式：scores[i] * n/(n−1) − mean * n/(n−1)。基线不含样本自身，因此是无偏的；不做标准差归一化。源码 core_algos.py::compute_rloo_outcome_advantage L612–636

4. KL 为什么有两条路径、三种估计

4.1 三种逐 token 估计

记采样 token 上的对数比 Δ_t = log π_θ(a_t|s_t) − log π_ref(a_t|s_t)。只有采样到的那个 token 的 log-prob 可用，因此 KL 只能用单样本估计量近似。verl 支持的估计量如下，括号内是配置别名。源码 core_algos.py::kl_penalty_forward L2216–2251

k1（kl） = Δ k2（mse） = ½·Δ² k3（low_var_kl）= e^{−Δ} + Δ − 1　　代码：kl = ref − logp；clamp(kl, ±20)；ratio = exp(kl)；clamp(ratio − kl − 1, −10, 10) abs = |Δ| full → NotImplementedError

在配置值后加 +（如 k3+）启用 straight-through：前向数值仍是原估计量，反向梯度换成 k2 的梯度，即 k2 − sg(k2) + sg(k_x)。源码注释给出的理由是：k1、k3 的期望等于 KL，但它们梯度的期望不等于 KL 的梯度；k2 的梯度才是正确的梯度估计。源码 core_algos.py::kl_penalty L2200–2213

补充下面用单步、on-policy（a ~ π_θ）、只看当前 token 的设定验证这条注释。记 ρ = π_ref(a)/π_θ(a)，并利用 E_{π_θ}[∇log π_θ] = 0： ∇k1 = ∇log π_θ → E[∇k1] = 0 ∇k2 = Δ·∇log π_θ → E[∇k2] = Σ_a ∇π_θ(a)·(log π_θ − log π_ref) = ∇ KL(π_θ ‖ π_ref) ∇k3 = (1 − ρ)·∇log π_θ → E[∇k3] = −Σ_a π_ref(a)·∇log π_θ(a) = ∇ KL(π_ref ‖ π_θ) 结论：把 k1 当 loss，期望梯度为 0，只剩噪声；k3 当 loss，得到的是 forward KL 的梯度，而不是 reverse KL；只有 k2 给出 reverse KL 的梯度。这一推导有两个前提需要记住：verl 的样本来自 π_old 或 π_rollout 而非 π_θ，只在第一个 mini-batch 上近似成立；逐 token 估计忽略了 θ 对后续状态分布的影响。

两条路径的本质区别在于 KL 的梯度经由哪条通道到达参数。路径 A 中，KL 是奖励的一部分，梯度来自策略梯度的 score function 项；路径 B 中，KL 是 loss 的一部分，梯度来自对 log_prob 的直接求导，因此估计量的选择（k1、k2、k3 及 +）在路径 B 中直接决定梯度的偏差。verl 的 GRPO 文档要求走路径 B（use_kl_loss=True）；PPO 文档同时列出两条路径，两个开关默认都是 False，即默认不启用 KL、也不创建 ref。引用 docs/algo/grpo.md、docs/algo/ppo.md

补充路径 A 配合 k1 时，把 −β·Σ_t k1 当作序列奖励，用 score function 求梯度，得到的正好是序列级 reverse KL KL(π_θ ‖ π_ref) 的无偏梯度——这是经典 RLHF 把 KL 放进奖励的理由。但在 GRPO 中，compute_grpo_outcome_advantage 先把 token_level_rewards 沿 token 求和，再做组内标准化，KL 项会被组内标准差缩放，逐 token 的结构也随之消失。

5. loss 聚合：分母决定谁的权重更大

policy loss、entropy loss 和 KL loss 都先得到形状为 [N_mb, T_r] 的逐 token loss 矩阵 L，再由 agg_loss 按 actor.loss_agg_mode（默认 token-mean）聚合成标量。记 M 为 response_mask，N_tok、N_seq 为整个 mini-batch、全部 DP rank 上的有效 token 数与序列数，D 为 DP 大小：

token-mean = Σ_{i,t} M·L / N_tok · D token-sum = Σ_{i,t} M·L · D seq-mean-token-sum = Σ_i (Σ_t M·L) / N_seq · D seq-mean-token-sum-norm = seq-mean-token-sum / C　　C = loss_scale_factor，未设置时取当前 micro-batch 的 T_r seq-mean-token-mean = Σ_i (Σ_t M·L / Σ_t M) / N_seq · D

源码 core_algos.py::agg_loss L1140–1206；losses.py L77–80、L164–181

5.1 为什么结果与 micro-batch 切分无关

一次 optimizer step 对应一个 mini-batch。FSDP engine 在 forward_backward_batch 开头先对该 mini-batch 的 loss_mask 求和，并在 DP 组内 all-reduce，得到全局 batch_num_tokens；随后把 mini-batch 切成若干 micro-batch，逐个前向、反向并累加梯度。源码 workers/engine/fsdp/transformer_impl.py L728–743；workers/engine/base.py::train_batch L113–131 每个 micro-batch 的 loss 是「本地 token 求和 ÷ 全局 token 数 × D」，梯度累加相当于对所有 micro-batch 求和，DP 梯度同步再除以 D，两者合起来正好是全局 mini-batch 上的 token 平均。seq 系列模式的 N_seq 来自 global_batch_size，由 _update_actor 设为 ppo_mini_batch_size × rollout.n。v1/trainer_base.py L1830–1831、L1856

因此，动态 batch（use_dynamic_bsz）按 token 预算重新打包 micro-batch，不会改变梯度的数学期望。会改变数值的是浮点求和顺序——这一点在第 4、8 章讨论 bitwise 一致时很重要。

8. 思考题

先独立作答，再展开参考答案。答案中的源码位置可以用第 9 节的命令复核。

Q1. sync 模式、ppo_epochs=1、第一个 mini-batch 上，PPO 比率 r_t 是否严格等于 1？如果不是，差异来自哪里？

参数相同，但通常不严格等于 1。old_log_probs 来自 compute_log_prob（无梯度，按 log_prob_micro_batch_size_per_gpu 或 log_prob_max_token_len_per_gpu 打包），log_prob 来自 train_batch（按 ppo_micro_batch_size_per_gpu 或 ppo_max_token_len_per_gpu 打包，可能开启 gradient checkpointing 或 fused kernel）；两套打包参数在 engine_workers.py L654–666 分别写入 engine 的 infer_* 与训练字段。只要 attention、GEMM、归约等 kernel 的累加顺序随 batch 组成变化，两次前向就不是 bitwise 一致的，r_t 是 1 附近的数值噪声。这是训练引擎内部的一致性问题，与推理引擎无关；第 4 章讲打包、第 8 章讲 batch invariance 时回到这里。

Q2. GRPO 中一组 n 条回复全部答对（或全部答错）时，优势是多少？这些样本对梯度还有什么影响？

组内 R_i − mean = 0，标准差为 0，0 / (0 + 1e-6) = 0，优势为 0，policy loss 的梯度贡献为 0。但这些 token 仍计入 token-mean 的分母 N_tok，会稀释其他样本的梯度；KL loss 与 entropy loss 也仍然作用于它们。DAPO 的 dynamic sampling（algorithm.filter_groups）用于过滤这类组，V1 中的入口是 PPOTrainer._resolve_filter_groups_metric，第 6 章讲 ReplayBuffer 时展开。

Q3. token-mean 为什么要乘 DP 大小 D？如果 8 个 DP rank 上的 token 数差别很大，结果还是全局平均吗？

FSDP/DDP 同步梯度时取各 rank 的平均，相当于除以 D。每个 rank 的 loss 是「本地 token 求和 ÷ 全局 token 数 × D」，平均之后为「所有 rank 的 token 求和 ÷ 全局 token 数」，正好是全局 token 平均，与各 rank 分到多少 token 无关。trainer.balance_batch 解决的是各 rank 计算量不均导致的等待，而不是 loss 口径。

Q4. 同样是 KL 惩罚，use_kl_in_reward 与 use_kl_loss 对 log-prob 的依赖有何不同？在 GRPO 中启用 KL 进奖励会发生什么？

前者在 driver 上用无梯度的 old_log_probs 与 ref_log_prob，KL 以 token 级奖励的形式进入优势估计；后者在 worker 上用带梯度的 log_prob，直接进 loss。GRPO 先把 token_level_rewards 沿 token 求和成标量，再做组内标准化，KL 变成序列奖励的一部分并被组内标准差缩放，逐 token 的 KL 结构消失。这是 GRPO 文档要求用 KL loss 的原因之一。

Q5. 8 卡、FSDP、不开 Ulysses SP（DP = 8），train_batch_size=1024、rollout.n=5、ppo_mini_batch_size=256、ppo_epochs=2。每 step 有多少条轨迹、多少次 optimizer step？每次 optimizer step 每卡处理多少条轨迹？

轨迹 1024 × 5 = 5120 条；optimizer step (1024 / 256) × 2 = 8 次；每个 mini-batch 256 × 5 = 1280 条，每卡 1280 / 8 = 160 条，再按 micro-batch 大小或 token 预算切分做梯度累加。开启 Ulysses SP 后 DP 变为 8 / sp_size，每卡条数随之增大。估算

Q6. 默认 γ = λ = 1 的 GAE 与 GRPO 都在估计 R − b。两者的基线 b 有什么本质区别？各自的代价是什么？

GAE 的 b = V(s_t) 由 critic 学出，随 token 位置变化，能区分同一条回复中不同前缀的好坏，代价是多训练一个与 actor 同规模的模型（显存、计算、values 与 update_critic 两个阶段）。GRPO 的 b 是同一 prompt 下 n 条回复的经验均值，对整条回复是常数，不需要 critic，代价是每个 prompt 必须采样多条，并且同一回复内所有 token 的优势相同，无法做 token 级的信用分配。
